JavaScript is the third leg of the web platform's original three-part stool: HTML for structure, CSS for presentation, JavaScript for behavior — anything that responds to a click, updates without a full page reload, or runs logic right in the browser. Despite the name, it has no real relationship to Java; the name was a marketing decision from 1995, when the language was created in ten days at Netscape to ride the popularity of Java applets at the time.

Today JavaScript runs in every major browser through its own engine (V8 in Chrome, SpiderMonkey in Firefox), and — thanks to Node.js — outside the browser entirely, on servers and in command-line tools, using the exact same language.

A <script> tag brings JavaScript into an HTML page. Placed with defer, it downloads in the background and runs only after HTML parsing finishes, in source order — the sensible default for most page scripts. console.log(...) is arguably the single most useful line in this entire guide: it prints a value to the browser's developer console, and reaching for it constantly to inspect what your code is actually doing is completely normal practice, not a crutch.

console.log("Hello, browser console!"); const message = "JavaScript runs the behavior layer."; console.log(message);
  • JS is behavior, sitting alongside HTML (structure) and CSS (presentation).
  • It runs in the browser via an engine, and outside the browser via Node.js.
  • console.log is the everyday tool for seeing what your code is actually doing.
Open your own browser's devtools console right now (F12, or Cmd+Option+J) and type console.log("hello") — you don't need a file or a server to start experimenting with JavaScript.

A variable is a named container for a value. Modern JavaScript gives you two everyday ways to declare one: let for a value you plan to reassign later, and const for one you don't — attempting to reassign a const throws an error, which is exactly the point: it documents intent and catches accidental reassignment early. A common convention is to reach for const by default and switch to let only once you genuinely need to reassign.

var is the original way to declare a variable, predating both, and it behaves differently in ways that cause real bugs. It's function-scoped rather than block-scoped, meaning a var declared inside an if block or a loop "leaks" out to the whole enclosing function, while let/const stay confined to the block they're declared in. var declarations are also hoisted to the top of their scope and initialized to undefined immediately, so referencing one before its declaration line silently gives undefined instead of an error — let/const stay in an unusable state until their declaration line actually runs, throwing a clear error if you touch them early instead of failing silently.

For all of these reasons, modern JavaScript treats var as legacy — reach for const/let in new code.

function example() { if (true) { let blockScoped = "only visible inside this block"; var functionScoped = "visible through the whole function"; } // console.log(blockScoped); // ReferenceError console.log(functionScoped); // works — var "leaked" out }
  • const by default; let when reassignment is genuinely needed.
  • var is function-scoped, not block-scoped — it leaks out of if-blocks and loops.
  • Modern JavaScript treats var as legacy — avoid it in new code.
Declaring a loop counter with var inside a loop that creates closures (like several setTimeout calls) is a classic bug, since every closure shares the same single var variable instead of each getting its own — covered fully in the closures topic later.

JavaScript is dynamically typed — a variable itself has no fixed type; whatever value it currently holds does, and that can change over the variable's lifetime. A handful of "primitive" types cover most everyday values: string (text), number (integers and decimals share one type — no separate int/float), boolean (true/false), undefined (a variable that's been declared but never assigned), and null (an explicit, intentional "no value," set deliberately by you rather than simply left absent). Everything else — arrays, objects, functions — is an object under the hood. typeof value tells you a value's type as a string, useful for debugging and the occasional runtime check.

JavaScript will also try to convert between types automatically in certain situations, called type coercion — "5" + 1 produces the string "51" (numbers get converted to a string when added to one), while "5" - 1 produces the number 4 (subtraction has no string meaning, so the string gets converted to a number instead). This inconsistency is exactly why === (strict equality, checking both value and type) is strongly preferred over == (loose equality, which silently coerces one side to match the other first) — "5" == 5 is true, which is rarely what you actually meant to ask.

typeof "hello"; // "string" typeof 42; // "number" typeof undefined; // "undefined" typeof null; // "object" (a famous, long-standing quirk) "5" == 5; // true — coerces types first, often surprising "5" === 5; // false — different types, no coercion, safer
  • JavaScript is dynamically typed — values have types, variables don't.
  • undefined means "never assigned"; null means "intentionally empty."
  • Always prefer === over == to avoid surprising type coercion.
== silently converts types before comparing, producing surprising results like "5" == 5 being true — use === by default.

Arithmetic operators (+ - * / % **) work as expected on numbers, with % giving the remainder of division (handy for checking even/odd, or alternating something every few items) and ** for exponentiation. Comparison operators (< > <= >= === !==) produce a boolean. Logical operators combine or check booleans: && (true only if both sides are true), || (true if either side is true), and ! (flips a boolean).

Beyond pure booleans, && and || are also used constantly for their "short-circuiting" behavior — || returns the first value that isn't "falsy" (a small set of values JavaScript treats as false in a boolean context: false, 0, "", null, undefined, NaN), which is how someValue || 'default' provides a fallback. ?? (nullish coalescing) is a more precise version of that same idea: it only falls back when the left side is specifically null or undefined, not for other falsy values like 0 — important when a legitimate value like the number zero shouldn't be treated as "missing."

The ternary operator, condition ? valueIfTrue : valueIfFalse, packs a simple if/else into a single expression that itself produces a value, unlike a full if statement.

const quantity = 0; quantity || 10; // 10 — 0 is falsy, so it falls back quantity ?? 10; // 0 — 0 is not null/undefined, so it's kept const label = quantity > 0 ? "In stock" : "Out of stock";
  • % gives the remainder, ** gives exponentiation.
  • || falls back on any falsy value; ?? falls back only on null/undefined.
  • The ternary operator is an if/else that produces a value, usable inline.

Strings can be written with single quotes, double quotes (functionally identical — pick one and stay consistent), or backticks, which create a "template literal" with two extra powers: multi-line text with no special escape characters, and ${...} interpolation, embedding any JavaScript expression directly inside the string — dramatically more readable than concatenating pieces together with +.

A handful of string methods come up constantly: .length (a property, not a method, giving the character count), .slice(start, end) extracts a substring, .split(separator) breaks a string into an array of pieces, .trim() removes leading/trailing whitespace, .includes(substring) checks for a substring's presence, and .toUpperCase()/.toLowerCase() change case. Strings are immutable — every one of these methods returns a brand-new string rather than modifying the original in place.

const name = "Amit"; const count = 3; const greeting = `Hi, ${name}! You have ${count + 1} new messages.`; const tags = "javascript, css, html"; const list = tags.split(", ").map(t => t.trim().toUpperCase()); // ["JAVASCRIPT", "CSS", "HTML"]
  • Template literals (backticks) support multi-line text and ${} interpolation.
  • Strings are immutable — every string method returns a new string.
  • Prefer template literals over + concatenation for readability.

An array is an ordered, numbered list of values, created with square brackets: const fruits = ['apple', 'banana', 'cherry'];. Access an item by its zero-based index — fruits[0] is 'apple' — and the last item's index is always fruits.length - 1, not fruits.length, a very common off-by-one trip-up for newcomers.

.push(item) adds to the end, .pop() removes from the end, .unshift(item) adds to the start, .shift() removes from the start — all four mutate the original array in place, unlike the string methods from the previous topic. A basic for loop visits every item by index; a more modern for...of loop visits every item directly with no index variable to manage at all, and is generally preferred for a simple "do something with every item" case.

const fruits = ["apple", "banana", "cherry"]; fruits.push("date"); // ["apple", "banana", "cherry", "date"] fruits[fruits.length - 1]; // "date" — the last item, correctly indexed for (const fruit of fruits) { console.log(fruit); }
  • Arrays are zero-indexed — the last valid index is length - 1.
  • push/pop/shift/unshift mutate the array in place.
  • for...of is the simpler modern way to visit every item.

An object stores data as named key/value pairs, created with curly braces: const user = { name: 'Amit', age: 28 };. Access a property with dot notation (user.name) when you know the property name ahead of time, or bracket notation (user['name'], or user[someVariable]) when the name itself needs to come from a variable. Objects nest arbitrarily — a value can itself be another object or an array — which is how real-world data, like a user profile or an API response, is typically shaped.

Object.keys(obj) returns an array of just the property names, Object.values(obj) returns just the values, and Object.entries(obj) returns an array of [key, value] pairs — the standard way to loop over an object's contents, since a plain for...of doesn't work directly on an object the way it does on an array.

const user = { name: "Amit", role: "engineer", address: { city: "Ghaziabad" } }; user.name; // "Amit" user["role"]; // "engineer" user.address.city; // "Ghaziabad" Object.keys(user); // ["name", "role", "address"]
  • Dot notation for known property names, bracket notation when the name is dynamic.
  • Objects nest arbitrarily to represent real-world structured data.
  • Object.keys/values/entries are the standard way to loop over an object.

A function packages up a reusable block of code. A function declaration is hoisted entirely — including its body — meaning you can call it earlier in a file than where it's actually written. A function expression stores an anonymous (or named) function in a variable instead, and is not hoisted the same way, so it can only be called after that line runs. An arrow function is a more compact syntax for a function expression, and — for a single-expression body — can drop both the curly braces and the return keyword entirely. Arrow functions also handle the this keyword differently from the other two forms, covered fully in its own topic later.

Parameters can have default values, used whenever the caller doesn't supply that argument. Whatever a function's return statement produces becomes the function call's own value; a function with no return statement at all implicitly returns undefined.

// Function declaration — fully hoisted function greetA(name) { return "Hi, " + name; } // Function expression — not hoisted const greetB = function (name) { return "Hi, " + name; }; // Arrow function, with a default parameter const greetC = (name = "friend") => `Hi, ${name}`;
  • Function declarations are fully hoisted; function expressions and arrow functions are not.
  • Arrow functions offer a compact single-expression shorthand.
  • A function with no return implicitly returns undefined.

if/else if/else branches based on a condition's truthiness. switch compares one value against several possible cases, useful when you'd otherwise write a long else if chain against the same variable — each case needs a break, or execution "falls through" into the next case, usually unintentionally.

Three loop forms cover repetition. A for loop is best when you need an index or a specific count of iterations. A while loop repeats as long as a condition stays true, checked before each pass — good when the number of iterations isn't known ahead of time. A do...while loop is identical to while except it checks the condition after the first pass, guaranteeing the body runs at least once even if the condition is already false. break exits a loop (or switch) immediately; continue skips straight to the next iteration without exiting.

function describe(size) { switch (size) { case "small": return "Fits in a pocket"; case "medium": return "Fits in a bag"; default: return "Bring a cart"; } } let attempts = 0; while (attempts < 3) { attempts++; }
  • Each switch case needs its own break, or it falls through into the next one.
  • while checks its condition before each pass; do...while checks after.
  • break exits a loop entirely; continue skips to the next iteration.
Forgetting break inside a switch case is a classic bug — execution quietly continues into the next case's code instead of stopping.

This is where JavaScript actually touches the page. document.querySelector('.card') returns the first element matching a CSS selector — any valid CSS selector works here, from a simple class to a complex combinator; document.querySelectorAll('.card') returns every matching element, as a static list.

Once you have an element, .textContent reads or sets its plain text safely, with no risk of the content being interpreted as markup, while .innerHTML reads or sets its actual HTML — powerful, but risky if fed unescaped user input. .classList.add(...)/.remove(...)/.toggle(...) manage an element's CSS classes directly, generally the cleanest way to change an element's appearance from script. document.createElement('div') builds a brand-new element entirely in memory, and .append(...) inserts it into the actual page.

const card = document.querySelector(".card"); card.classList.toggle("is-active"); const note = document.createElement("p"); note.textContent = "Added by JavaScript"; card.append(note);
  • querySelector/querySelectorAll accept any CSS selector, exactly like a stylesheet would.
  • textContent is safe for plain text; innerHTML risks the XSS issue if fed unescaped input.
  • classList is generally the cleanest way to change appearance from script.

element.addEventListener('click', handlerFunction) runs handlerFunction every time that element is clicked — the standard way to respond to interaction, replacing the older inline onclick="..." attribute pattern. The handler receives an event object as its argument, and event.target is the specific element the event actually originated from, which matters once elements are nested.

Events "bubble" upward by default: a click on a button inside a card fires the button's handler first, then the card's (if it has one), then further up the tree. This bubbling is what makes "event delegation" possible — instead of attaching a separate listener to a hundred individual list items, attach one listener to their shared parent and check event.target inside it to figure out which child was actually clicked, far more efficient, and it automatically covers items added later. event.preventDefault() stops an event's default browser behavior — most commonly, stopping a form's submit from actually reloading the page.

const list = document.querySelector(".todo-list"); list.addEventListener("click", (event) => { if (event.target.matches(".todo-item")) { event.target.classList.toggle("done"); } });
  • addEventListener is the standard way to respond to interaction.
  • Events bubble upward through ancestors by default, enabling event delegation.
  • preventDefault() stops the browser's default behavior for that event.

These three methods, together with forEach, cover the vast majority of everyday array work, and all four take a function that runs once per item. forEach just runs a function per item for a side effect (like logging) and returns undefined — it doesn't build anything. .map(fn) returns a brand-new array by transforming every item — same length, different content. .filter(fn) returns a new array containing only the items where fn returns something truthy — same or shorter length.

.reduce(fn, initialValue) is the most flexible: it walks the array building a single accumulated result, calling fn(accumulator, currentItem) at each step and carrying the return value forward as the new accumulator. None of the three mutate the original array — each returns a fresh one, which is exactly why they chain together cleanly.

const orders = [12, 45, 8, 90, 33]; const total = orders .filter(amount => amount > 10) .map(amount => amount * 1.18) .reduce((sum, amount) => sum + amount, 0);
  • map transforms every item into a new array of the same length.
  • filter keeps only matching items.
  • reduce folds the array down into one accumulated value.

Destructuring unpacks values out of an array or object into individual named variables in one line. Array destructuring goes by position; object destructuring goes by property name, and can rename on the way out or supply a default for a property that might be missing.

The spread operator, ..., expands an array or object out into individual elements or properties — { ...obj1, ...obj2 } merges two objects into a new one, with later properties overriding earlier ones on a collision — an extremely common pattern for updating one property immutably, without mutating the original. The rest parameter uses the exact same ... syntax in the opposite direction: gathering any remaining function arguments into a real array.

const user = { name: "Amit", role: "engineer", age: 28 }; const { name, role = "guest" } = user; const updated = { ...user, age: 29 }; // new object, original untouched function sum(...numbers) { return numbers.reduce((a, b) => a + b, 0); } sum(1, 2, 3); // 6
  • Destructuring unpacks array items by position, or object properties by name.
  • Spread (...) expands a collection out — the standard pattern for updating an object immutably.
  • Rest (same ... syntax, opposite direction) gathers arguments into an array.

JavaScript uses lexical scope — a function can access any variable declared in the scope it was physically written inside, no matter where it later gets called from. A closure is what happens when an inner function is returned or passed elsewhere and keeps that access alive even after the outer function has already finished running: it "closes over" those outer variables, remembering rather than losing them.

Each call to a function that returns another function creates a genuinely separate, private set of variables that nothing outside can reach directly — a real, practical way to create private state without a class. The classic closure gotcha involves var inside a loop: because var is function-scoped, every closure created inside a var-based loop shares the exact same variable, so by the time any of them run, they all see the loop's final value. Switching to let fixes it immediately, since let creates a fresh binding for each iteration.

function makeCounter() { let count = 0; return function () { count++; return count; }; } const counter = makeCounter(); counter(); // 1 counter(); // 2 — count is private to this specific counter
  • A closure is an inner function retaining access to its outer function's variables.
  • Closures are a real way to create private state.
  • The classic var-in-a-loop bug happens because every iteration shares one binding — let fixes it.

this is confusing because its value isn't fixed by where a function is defined — it's determined by how that function is actually called, its "call site." Called as a method (user.greet()), this is the object left of the dot. Called as a plain, unattached function, this is undefined in strict mode — exactly why a method casually passed around as a callback so often "loses" its this.

Arrow functions are the major exception: they don't have their own this at all — they use whatever this was in effect in the surrounding code where they were written, the same lexical rule closures use for ordinary variables — which is why arrow functions have become the default choice for callbacks that need an outer this. .bind(thisValue) returns a brand-new function permanently locked to a chosen this, commonly used to fix this problem for a plain function.

const button = { label: "Save", onClick: function () { console.log(this.label); } }; setTimeout(button.onClick, 100); // logs undefined — lost "this" setTimeout(() => button.onClick(), 100); // logs "Save" — arrow keeps it
  • this is determined by how a function is called, not where it's defined.
  • Arrow functions don't have their own this — they inherit it from the surrounding code.
  • bind permanently locks a function to a chosen this.

JavaScript runs on a single thread — one call stack, doing exactly one thing at a time — yet browsers routinely juggle network requests, timers, and animations all "at once" without freezing. The trick is the event loop: slow operations are handed off to the browser to handle in the background, and only once they finish does their callback get queued to run on the main thread, whenever it's next free.

A callback is simply a function passed into another function to be run later, once some operation completes. The trouble starts once several asynchronous steps need to happen strictly in sequence, each depending on the previous one's result — nesting callback inside callback produces the infamous "callback hell," deeply indented and genuinely hard to follow. That real problem is exactly what promises, the next topic, were designed to solve.

getUser(id, (user) => { getOrders(user.id, (orders) => { getInvoice(orders[0].id, (invoice) => { console.log(invoice); // three levels deep, and growing }); }); });
  • JavaScript runs on a single thread; the event loop hands off slow work and runs callbacks later.
  • This doesn't block other code from running in the meantime.
  • Deeply nested callbacks for sequential steps produce hard-to-read "callback hell."

A Promise represents a value that isn't available yet but will be eventually — the eventual result of an asynchronous operation. It exists in one of three states: pending, fulfilled (succeeded, with a value), or rejected (failed, with a reason). .then(onFulfilled) registers a function to run once it fulfills; .catch(onRejected) runs if it rejects instead; .finally(fn) runs regardless, useful for cleanup like hiding a loading spinner either way.

Crucially, .then() itself returns a new promise, which is what makes chaining work — each step runs only after the previous one resolves, replacing callback hell's nested pyramid with a flat sequence. Promise.all([p1, p2, p3]) waits for every promise to fulfill and is the standard way to run several independent operations concurrently rather than one after another.

getUser(id) .then(user => getOrders(user.id)) .then(orders => console.log(orders)) .catch(error => console.error(error)); Promise.all([getUser(1), getUser(2)]) .then(([userA, userB]) => console.log(userA, userB));
  • A promise is pending, then eventually fulfilled or rejected, exactly once.
  • .then() chaining replaces nested callback pyramids with a flat sequence.
  • Promise.all runs several promises concurrently and waits for all of them.

async/await is syntax sugar sitting directly on top of promises — it doesn't replace them, it lets code that uses them read like ordinary, top-to-bottom code. Marking a function async makes it always return a promise automatically; inside it, await somePromise pauses execution at that line — without blocking the rest of the page — until the promise settles, then hands back its resolved value directly.

Error handling switches from .catch() to an ordinary try/catch block around the await calls. One genuine trap: awaiting several independent operations one after another runs them sequentially even though they don't depend on each other — when they're genuinely independent, await Promise.all([...]) runs both at once and is measurably faster.

async function loadDashboard(id) { try { const [user, orders] = await Promise.all([ getUser(id), getOrders(id) ]); return { user, orders }; } catch (error) { console.error("Failed to load dashboard:", error); } }
  • async/await is syntax sugar over promises.
  • Errors are caught with ordinary try/catch around the await.
  • Independent awaits should run via Promise.all in parallel, not one after another.
Awaiting several unrelated operations one after another, instead of with Promise.all, needlessly serializes work that could have run concurrently.

fetch(url) sends an HTTP request and returns a promise that resolves once the response's headers arrive — even for an error response like a 404, since fetch only rejects on an actual network failure, never on an HTTP error status by itself. Real code checks response.ok explicitly before trusting the result. response.json() reads and parses the body as JSON, itself returning another promise — which is why a typical fetch involves two awaits in a row.

JSON (JavaScript Object Notation) is a plain-text data format that looks almost like a JavaScript object literal but with stricter rules — property names always need double quotes, and it can't contain functions or comments. JSON.stringify(value) converts a JavaScript value into a JSON string, exactly what you send in a POST body; JSON.parse(jsonString) does the reverse.

async function createUser(data) { const response = await fetch("/api/users", { method: "POST", headers: { "Content-Type": "application/json" }, body: JSON.stringify(data) }); if (!response.ok) { throw new Error(`Request failed: ${response.status}`); } return response.json(); }
  • fetch only rejects on a genuine network failure — always check response.ok.
  • response.json() returns its own promise, needing its own await.
  • JSON.stringify/parse convert between a JS value and its JSON text form.

try { ... } catch (error) { ... } runs the try block, and if anything inside throws, execution jumps to the catch block instead of crashing the script. An optional finally { ... } block runs afterward regardless of the outcome, ideal for cleanup that must happen either way.

throw new Error('Something specific went wrong') is the conventional way to raise your own errors — an Error object captures a stack trace automatically, invaluable for tracking down where a problem originated. Not every error should be caught at the point it occurs — sometimes the right choice is to let it bubble up to a higher level of the code that's in a better position to decide what the user should see or whether to retry.

function withdraw(balance, amount) { if (amount > balance) { throw new Error("Insufficient funds"); } return balance - amount; } try { withdraw(100, 500); } catch (error) { console.error(error.message); } finally { console.log("Transaction attempt finished"); }
  • try/catch stops a thrown error from crashing the whole script.
  • throw new Error(message) is the conventional way to raise your own errors.
  • Not every error should be caught immediately — sometimes it should bubble up.

Every JavaScript object has an internal link to another object called its prototype, and when you access a property that isn't found directly on the object itself, JavaScript keeps looking up that chain of prototypes until it finds the property or runs out of chain — this is prototypal inheritance, the mechanism underneath nearly everything in the language, including why every plain object has methods like .toString() available without you ever defining them. Object.create(protoObject) creates a new object with its prototype explicitly set to whatever you pass in — the most direct way to build this relationship by hand.

Every function also has a .prototype property — when you call a function with new, the resulting object's internal prototype gets set to that function's .prototype, which is exactly the low-level mechanism the class syntax in the next topic is actually built on top of. Classes didn't replace prototypes; they gave them a cleaner, more familiar syntax.

const animal = { speak() { return `${this.name} makes a sound.`; } }; const dog = Object.create(animal); dog.name = "Rex"; dog.speak(); // "Rex makes a sound." — found via the prototype chain
  • Objects look up a chain of prototypes for properties they don't have directly.
  • Object.create() builds this relationship explicitly.
  • The class syntax (next topic) is sugar over this exact same prototype mechanism.

class syntax gives object-oriented code a familiar, readable shape, even though it compiles down to the same prototype mechanism underneath. A constructor method runs automatically when you create an instance with new, typically used to set up initial properties; other methods are automatically shared via the prototype chain rather than duplicated onto every instance.

extends sets up inheritance between classes, and super(...) inside a subclass's constructor calls the parent's constructor, required before using this in a subclass constructor at all. static methods and fields belong to the class itself rather than any instance. A # prefix on a field or method marks it genuinely private, enforced by the language itself — completely inaccessible from outside the class.

class Account { #balance; constructor(owner, balance = 0) { this.owner = owner; this.#balance = balance; } deposit(amount) { this.#balance += amount; return this.#balance; } } class SavingsAccount extends Account { constructor(owner, balance, rate) { super(owner, balance); this.rate = rate; } }
  • Class syntax is sugar over prototypes, not a separate inheritance system.
  • extends/super set up and initialize inheritance between classes.
  • A # prefix creates a field the language itself enforces as private.

The event loop actually manages two separate queues of pending work. The "macrotask" queue holds things like setTimeout callbacks and user input events. The "microtask" queue holds promise callbacks — everything an await resumes into. After every single macrotask finishes, the event loop always drains the entire microtask queue completely before moving on to the next macrotask — which is exactly why a resolved promise's .then() reliably runs before a setTimeout(fn, 0) callback, even though the timeout was technically requested to fire "immediately."

This matters whenever you're reasoning about the precise order several asynchronous operations will run in, especially when mixing promise chains with timers.

console.log("1: sync"); setTimeout(() => console.log("2: macrotask (setTimeout)"), 0); Promise.resolve().then(() => console.log("3: microtask (promise)")); console.log("4: sync"); // Actual order: 1, 4, 3, 2 // Microtasks always drain before the next macrotask runs.
  • The microtask queue (promise callbacks) is always fully drained before the next macrotask runs.
  • This is why a resolved promise's .then() runs before a setTimeout(fn, 0).

An ES module is a JavaScript file with its own private scope — nothing declared inside it is automatically visible to any other file, unlike old-fashioned scripts that all shared one global scope. export makes a value, function, or class available to other files — a "named" export, of which a file can have any number, or a file's single "default" export. Another file brings those in with import, matching a named export's exact name, or choosing any local name for a default export.

A <script type="module"> tag, rather than a plain <script>, tells the browser to treat a file as a module — enabling import/export — and modules are automatically deferred, run only after parsing, exactly like the defer attribute. In real projects with many files, a bundler typically combines everything into fewer, optimized files for production, but the import/export syntax you write is identical either way.

export const TAX_RATE = 0.18; export default function formatPrice(amount) { return `₹${amount.toFixed(2)}`; } // In another file: // import formatPrice, { TAX_RATE } from './constants.js';
  • Each module has its own private scope, unlike old shared-global-scope scripts.
  • Named exports import by their exact name; a default export can be imported under any local name.
  • type="module" enables this and behaves like defer automatically.

In JavaScript, a function is a value like any other — it can be stored in a variable, passed as an argument, or returned from another function. A "higher-order function" is simply a function that takes another function as an argument, returns one, or both — map/filter/reduce are all higher-order functions, and so is any function that returns a closure.

A "pure" function always produces the same output for the same input and causes no observable side effects outside itself. Pure functions are easier to test and reason about, since calling one twice with the same arguments is always safe and predictable. "Composing" functions means feeding one function's output directly into another's input to build a pipeline out of simpler pieces, rather than one large function doing everything at once.

const withTax = price => price * 1.18; const format = price => `₹${price.toFixed(2)}`; const finalPrice = price => format(withTax(price)); finalPrice(100); // "₹118.00" — two small, pure functions composed
  • Functions are ordinary values in JavaScript — they can be passed around like any other value.
  • A pure function's output depends only on its input, with no outside side effects.
  • Composing small, focused functions together is generally more testable than one large function.

An iterator is any object implementing a next() method that returns { value, done } — a standard protocol JavaScript uses internally for for...of loops and the spread operator, letting them work on arrays, strings, and any custom object that opts in. A generator function — declared with function* and using yield — is a much easier way to build one than implementing the raw protocol by hand: calling it doesn't run the body immediately; it returns a special iterator, and each call to .next() runs up to the next yield, pausing there, and resumes exactly where it left off on the following call.

This pause-and-resume ability suits a sequence produced lazily, one value at a time, rather than computed and stored all at once — useful for something expensive to compute in full, or conceptually infinite.

function* countTo(n) { for (let i = 1; i <= n; i++) { yield i; } } for (const num of countTo(3)) { console.log(num); // 1, 2, 3 }
  • An iterator exposes a next() method returning { value, done }.
  • A generator function (function*/yield) is the easy way to build one.
  • Well suited to lazy or effectively infinite sequences.

localStorage.setItem(key, value)/.getItem(key) persist small string values in the browser. Since storage only holds strings, saving anything more structured means JSON.stringify() going in and JSON.parse() coming back out.

Two lesser-known but genuinely useful browser APIs solve specific problems elegantly. IntersectionObserver efficiently detects when an element scrolls into or out of the viewport — the modern way to implement lazy-loading or infinite-scroll, without manually checking scroll position on every scroll event. MutationObserver watches part of the DOM and fires a callback whenever it changes, useful for reacting to changes made by code you don't control directly.

const observer = new IntersectionObserver((entries) => { entries.forEach(entry => { if (entry.isIntersecting) { entry.target.classList.add("visible"); } }); }); document.querySelectorAll(".fade-in").forEach(el => observer.observe(el));
  • Storage APIs only hold strings — serialize structured data with JSON.stringify/parse.
  • IntersectionObserver is the efficient modern way to detect an element entering the viewport.
  • MutationObserver reacts to DOM changes you don't directly control.

Some events — scrolling, resizing, typing — can fire dozens of times per second, and running an expensive handler on every single one quickly overwhelms the browser. Debouncing delays running the handler until events have actually stopped arriving for a specified pause — perfect for a search-as-you-type box, where you only want to fire the request once typing pauses. Throttling instead guarantees the handler runs at most once per interval no matter how continuously events keep arriving — better suited to a scroll handler, where you genuinely want periodic updates throughout.

function debounce(fn, delay) { let timer; return (...args) => { clearTimeout(timer); timer = setTimeout(() => fn(...args), delay); }; } const search = debounce((query) => runSearch(query), 300); input.addEventListener("input", (e) => search(e.target.value));
  • Debouncing waits for a pause in events before running — right for search-as-you-type.
  • Throttling guarantees a maximum rate no matter how continuous the events are.
  • Both exist to protect the browser from an expensive handler running far too often.

JavaScript manages memory automatically through garbage collection — the engine periodically finds objects nothing can reach anymore and frees their memory. A memory leak happens when something keeps a reference to an object alive that should genuinely be free to go — the most common real-world cause is a forgotten event listener or setInterval timer that keeps referencing DOM elements or data long after they're needed. Removing an element from the DOM doesn't free its memory if a stray reference still points to it, a "detached DOM node," invisible on the page but still alive in memory.

Beyond memory specifically, the browser's devtools Performance panel can record exactly where time goes during a slow interaction, and profiling the actual bottleneck is a much better use of time than guessing.

  • Garbage collection reclaims memory automatically, but only for objects nothing can still reach.
  • Forgotten event listeners and timers are the most common real-world cause of a leak.
  • Profile the actual bottleneck with devtools before optimizing based on a guess.

A design pattern is a named, reusable solution to a recurring structural problem — worth knowing mainly so you can recognize and discuss them, not because every project needs one forced in. The module pattern uses a closure to expose only a chosen public interface while keeping details private — largely superseded by real ES modules, but still the conceptual root of "public API, private internals." The singleton pattern ensures only one instance of something ever exists across an app.

The observer pattern lets subscriber functions register interest in an event and get notified when it happens — you've already used this constantly, since it's exactly what addEventListener is. The factory pattern is a function whose job is creating and configuring objects of a certain shape, so construction logic lives in one obvious place.

function createEmitter() { const listeners = []; return { on(fn) { listeners.push(fn); }, emit(data) { listeners.forEach(fn => fn(data)); } }; } const cartEvents = createEmitter(); cartEvents.on(item => console.log("Added:", item)); cartEvents.emit("Blue mug");
  • These are named, recognizable solutions to recurring problems, not mandatory rules.
  • The observer pattern is one you've already been using — addEventListener implements it.
  • Recognizing a pattern by name makes discussing code with others considerably easier.

TypeScript is a superset of JavaScript — every valid JavaScript file is already valid TypeScript — that adds an optional static type system checked before the code ever runs, then compiled down to plain JavaScript. Declaring a variable's type lets tooling catch a whole category of mistakes (passing a string where a number was expected) at write-time, in your editor, rather than discovering them later at runtime.

Type annotations are stripped away entirely during compilation — they have zero effect on the running code or its performance. Many teams adopt it on any codebase past a certain size, where the editor autocompletion and refactoring safety it enables become a substantial, compounding time-saver.

function greet(name: string): string { return `Hi, ${name}`; } greet("Amit"); // fine greet(42); // caught at compile time, before it ever runs
  • TypeScript is a strict superset of JavaScript that adds compile-time type checking.
  • Type annotations are stripped away entirely before the code runs — zero runtime cost.
  • Teams commonly adopt it for earlier error-catching and editor tooling as a codebase grows.

An automated test runs a small piece of code and checks it behaves as expected, without a human manually clicking through the app to verify — the real payoff shows up the second time you touch that code, when the test immediately flags whether a change accidentally broke something. A unit test checks one small, isolated piece, usually a single function; an integration test checks that several pieces genuinely work together.

Testing frameworks share a broadly similar shape: describe(...) groups related tests, and it(...) defines one test case, typically ending in an assertion that fails the test if it doesn't hold. "Mocking" replaces a real dependency — a network call, the current date — with a fake, controlled stand-in during a test, so the outcome depends only on the code actually being tested.

function sum(a, b) { return a + b; } describe("sum", () => { it("adds two positive numbers", () => { expect(sum(2, 3)).toBe(5); }); });
  • Automated tests pay off most the second time code is touched, catching regressions immediately.
  • A unit test isolates one small piece; an integration test checks several pieces together.
  • Mocking swaps a real, unpredictable dependency for a controlled fake during a test.

Sixteen questions that come up often in real interviews, drawn from across every tier of this guide. Click a question to reveal a concise model answer — try answering in your own words first.

What's the difference between let, const, and var?

let and const are block-scoped; const additionally can't be reassigned. var is function-scoped and hoisted in a way that causes real bugs — avoid it in new code.

What's the difference between == and ===?

== coerces types before comparing; === checks both type and value with no coercion. Prefer === by default.

What is a closure?

An inner function that retains access to its outer function's variables even after the outer function has already finished running.

Explain event bubbling and event delegation.

Events propagate upward through ancestor elements by default. Delegation attaches one listener to a shared parent and inspects event.target to determine which child was actually interacted with.

What's the difference between map and forEach?

map returns a new, transformed array. forEach just runs a function per item for a side effect and returns undefined.

What does this refer to in a regular function versus an arrow function?

In a regular function, this is determined by the call site. An arrow function has no this of its own — it inherits it from the surrounding lexical scope.

What's the difference between a Promise and async/await?

async/await is syntax sugar over promises, letting asynchronous code read top-to-bottom like synchronous code.

Why does a resolved Promise's .then() run before a setTimeout(fn, 0)?

The microtask queue (promise callbacks) is always fully drained before the event loop moves on to the next macrotask, which is where setTimeout callbacks live.

What's the difference between null and undefined?

undefined means a variable was never assigned a value. null is an explicit, intentional "no value" that you set deliberately.

What is prototypal inheritance?

Objects look up a chain of linked prototype objects for properties or methods they don't have directly on themselves.

What does the spread operator do, and how does it differ from rest?

Spread expands a collection out into individual elements or properties. Rest, using the identical ... syntax, does the opposite — gathering individual arguments into an array. The direction is the difference.

Why do many patterns favor not mutating state directly?

Treating data as immutable and preferring pure functions makes code more predictable and testable, since a value can't have changed unexpectedly somewhere else in the program.

What is debouncing, and when would you use it?

Delaying execution until a burst of events has actually stopped arriving for a pause — ideal for a search-as-you-type input, so a request only fires once typing settles.

What does Array.prototype.reduce do?

It folds an array down into a single accumulated value, calling a function with the running accumulator and the current item at each step.

What's a memory leak in JavaScript, and what commonly causes one?

An object that should be collectible but is kept alive by a lingering reference — most often a forgotten event listener or an active timer that's never cleared.

What is a pure function?

A function whose output depends only on its input, with no observable side effects outside itself — calling it twice with the same arguments always gives the same result.

Twelve recurring mistakes gathered from across this guide, in one place for a final pass before you consider yourself done.

Using == instead of ===
Leads to surprising type coercion — prefer strict equality by default.
var inside a loop that creates closures
Every closure shares the same single binding — switch to let.
Forgetting break in a switch case
Execution quietly falls through into the next case.
Assuming spread makes a deep copy
{ ...obj } only copies one level deep — nested objects/arrays are still shared references.
Losing this when passing a method as a callback
Use an arrow function wrapper or .bind() to preserve it.
Awaiting independent promises sequentially
Needlessly serializes work that Promise.all could run concurrently.
Not checking response.ok after fetch
fetch doesn't reject on HTTP error statuses like 404 by itself.
Off-by-one on array length versus last index
The last valid index is length - 1, not length.
Assuming array methods like map/filter mutate
They return a new array — the original is left untouched.
Comparing objects or arrays with ===
Always false unless it's literally the same reference, never a deep comparison.
Forgetting an async function always returns a promise
Even a synchronous-looking return value needs an await at the call site.
A forgotten setInterval or event listener
The most common real-world cause of a memory leak.

Reading a guide gets you to recognition; writing JavaScript from scratch gets you to fluency. A few ways to close that gap:

  • Build a small to-do list app using only DOM methods and events, no framework, to solidify the DOM and events topics.
  • Rewrite a chain of nested callbacks into promises, then again into async/await, and compare readability.
  • Implement your own debounce function from scratch without looking at the guide's example.
  • Build a tiny event emitter and use it to decouple two unrelated pieces of code.
  • Write a few unit tests for a pure function you've already written.

Because JavaScript keeps evolving, treat MDN (developer.mozilla.org) as your ongoing reference for exact, current syntax whenever you need it — this guide is a foundation to build fluency on, not the last word on any single method.
