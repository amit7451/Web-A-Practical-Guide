Every guide in this series so far has treated HTML, CSS, and JavaScript as three separate languages, each with its own syntax and rules. This guide asks a different question: when a browser actually loads a page, what really happens to those three languages, in what order, on what hardware, and how do they actually touch each other at runtime? Everything that follows builds toward one complete, accurate mental model — by the end, you should be able to trace, in detail, exactly what a browser does between the moment you press Enter on a URL and the moment pixels appear on your screen, and exactly how a modern JavaScript framework sits on top of that same machinery.

At the highest level, five broad phases happen, roughly in sequence but with real overlap between them, which later modules unpack one at a time:

  1. Navigation — the browser resolves the URL's domain to an IP address (DNS), opens a secure connection (TCP and TLS), and sends an HTTP request.
  2. Parsing — as the HTML response streams in, the browser tokenizes and parses it into the DOM tree, discovering and fetching CSS and JavaScript along the way.
  3. Style and layout — CSS is parsed into the CSSOM, combined with the DOM into a render tree, and the browser computes the exact size and position of every visible box.
  4. Paint and composite — the browser turns those geometric boxes into actual pixels, often across several independently-managed layers that a separate thread composites together for the final image.
  5. Scripting and interaction — JavaScript executes throughout this whole process (not only at the end), reading and mutating the DOM and CSSOM, responding to events, and potentially triggering some or all of the steps above to run again.

The crucial idea to hold onto from this first module, which the rest of this guide exists to justify in detail: HTML, CSS, and JavaScript are not three independent tracks that happen to run at the same time. They are three inputs into one shared, ongoing pipeline, and JavaScript in particular can reach into almost any stage of that pipeline and force it to re-run. Understanding where the pipeline's expensive steps are, and which JavaScript operations force them to re-run, is the single most practical payoff of everything covered here — it's the actual reasoning behind nearly every performance rule stated as a flat fact in the HTML, CSS, and JavaScript guides ("prefer transform over top," "batch your DOM reads and writes," "microtasks run before the next macrotask"). Those rules stop being things to memorize once you can see the machine that makes them true.

  • Navigation, parsing, style/layout, paint/composite, and scripting are the five broad phases — overlapping, not strictly sequential.
  • HTML, CSS, and JS feed into one shared rendering pipeline, not three independent tracks.
  • JavaScript can reach into nearly any stage of that pipeline and force it to re-run — this is the real reason behind most performance advice in the earlier guides.

A modern browser is not one program — it's several separate operating-system processes working together, a design every major browser engine converged on for the same two reasons: stability (one crashed tab shouldn't take down the whole browser or your other tabs) and security (a compromised web page should be trapped in a heavily restricted sandbox, unable to touch your files or other tabs directly).

A simplified Chromium-style multi-process architecture. Each renderer process is sandboxed and typically isolated per site.

The browser process is the one true orchestrator: it owns the address bar, tab strip, bookmarks, and disk access, and it's the only process with unrestricted access to your operating system. The renderer process is where HTML parsing, CSS parsing, layout, and JavaScript execution actually happen — modern browsers give each site (not just each tab) its own renderer process where possible, a policy usually called site isolation, specifically so a malicious or buggy page in one tab can't read memory belonging to a different site open in another tab. The GPU process handles the final compositing and rasterization step (covered fully in the paint/composite module), offloading that work to graphics hardware. A network process centralizes DNS lookups, TLS handshakes, HTTP requests, and the disk cache, so every renderer process shares one consistent, centrally-managed cache and connection pool rather than each tab managing its own.

Every renderer process runs inside a strict OS-level sandbox: by design, it cannot directly open files, access arbitrary network sockets, or talk to other processes except through tightly controlled inter-process communication (IPC) channels back to the browser process. This is precisely why a web page cannot simply read a file from your hard drive, no matter what JavaScript runs inside it — the renderer process itself is physically incapable of the underlying system call, regardless of what the script tries to do.

  • A browser is several cooperating OS processes, not one program — for crash isolation and security.
  • The renderer process is where HTML/CSS parsing, layout, and JS execution happen — and modern browsers isolate it per site.
  • A sandboxed renderer process cannot touch the filesystem or other processes directly, no matter what JavaScript inside it tries to do.

Inside a single renderer process, most of the work this entire guide is about — HTML parsing, CSS parsing, style calculation, layout, most of paint, and every line of your JavaScript — happens on one specific thread, universally called the main thread (this is the exact same "single thread" the JavaScript guide's event loop topic referred to; this module explains what else is competing for time on it). The main thread genuinely does one thing at a time — it cannot run two of your event handlers simultaneously, and it cannot run your JavaScript and recalculate layout at the same literal instant. Everything the main thread needs to do gets interleaved: a task here, a layout recalculation there, a paint step, a batch of microtasks, back to another task.

This single-thread design is a deliberate trade-off, not an oversight. It sidesteps an entire category of hard problems: your JavaScript never needs a lock or a mutex to safely read or write the DOM, because nothing else can possibly be touching it at the same instant your code runs. The cost of that simplicity is exactly what the JavaScript guide's memory/performance topic warned about: a slow synchronous function, a very large loop, or an expensive layout recalculation genuinely freezes everything else on that thread — the page stops responding to clicks, scrolling stutters, animations stop — because there is no other main-thread work happening concurrently to pick up the slack.

Two escape hatches exist, and both matter for the application-layer modules later in this guide. First, a small number of expensive operations — most notably compositing, covered in the paint module — are deliberately handed off to a separate compositor thread inside the same renderer process, specifically so that scrolling and certain animations can keep running smoothly even while the main thread is briefly busy. Second, genuinely heavy computation can be moved off the main thread entirely using a Web Worker, a real, separate thread with its own event loop that simply cannot touch the DOM directly — covered in full in this guide's application-layer part, once the DOM itself has been properly introduced.

  • HTML/CSS parsing, layout, most paint work, and all your JavaScript share one main thread inside the renderer process.
  • Single-threaded execution avoids needing locks around the DOM, at the cost of one slow function freezing everything else.
  • A separate compositor thread and, for heavy computation, Web Workers are the two ways work escapes the main thread.
This is the same thread — and the same event loop — the JavaScript guide's event loop topic described. This guide adds the missing piece: that thread isn't only running your callbacks, it's running the entire rendering pipeline too, competing for the same time.

An HTML response arrives at the browser as a stream of raw bytes, not text — the first real step is decoding those bytes into characters using the encoding declared by the <meta charset> tag (or an HTTP header), exactly the mechanism the HTML guide's entities topic assumed but didn't explain the origin of. From there, HTML parsing runs in two connected stages: tokenization, which scans the character stream and produces a sequence of tokens (start tag, end tag, text, comment, and so on), and tree construction, which consumes those tokens one at a time and builds the actual DOM tree — the same tree structure document.querySelector and every other DOM API in the JavaScript guide operate on.

The HTML guide mentioned, almost in passing, that HTML parsing is deliberately fault-tolerant — unknown tags are treated as unstyled inline elements, and the page keeps rendering. This module explains the mechanism behind that: the HTML specification defines an extremely detailed, exact algorithm for exactly how to recover from broken markup — a missing closing tag, mismatched nesting, text in the wrong place — and every major browser implements that same recovery algorithm identically. This is precisely why a page with genuinely invalid HTML still renders consistently, the same way, in every browser: fault tolerance isn't each browser guessing independently, it's a fully specified, standardized behavior.

Critically, this parsing is incremental and streaming, not all-or-nothing: the browser begins tokenizing and building the DOM as soon as the first bytes arrive, without waiting for the entire HTML document to finish downloading — this is exactly why a large page's top content can appear before the rest has even arrived over the network, and it's the reason "placement in the document" (covered in the HTML guide's performance topic) has a real, physical effect on load time. While doing this, the browser also runs a preload scanner alongside the main parser — a lightweight secondary scan that looks ahead in the still-arriving HTML purely to spot references to other resources (images, stylesheets, scripts) and start fetching them immediately, before the main parser has even reached that point in the document. This is why a <script> or <link> near the top of a file doesn't have to fully block every other resource from starting its download, even though it may still block rendering — those are two genuinely separate concerns this module's later companions unpack fully.

<p>This paragraph is <b>never closed <p>The parser recovers and starts a new paragraph anyway, closing the previous one automatically — exactly as the spec requires.
  • HTML parsing is tokenization (chars → tokens) followed by tree construction (tokens → DOM).
  • Error recovery from broken markup is a fully specified algorithm, not per-browser guessing — which is why it renders the same everywhere.
  • Parsing is incremental and streaming, and a separate preload scanner starts fetching resources before the main parser even reaches them.

CSS is parsed in essentially the same two-stage shape as HTML — tokenizing raw text into meaningful pieces (selectors, properties, values), then building a tree — but the resulting structure is a separate tree entirely, the CSSOM (CSS Object Model), not part of the DOM. Every stylesheet a page loads (external, internal <style>, and inline style attributes, from the CSS guide's very first module) eventually feeds into this one shared CSSOM.

One detail explains a whole category of behavior from the CSS guide's cascade module: CSS parsing itself doesn't resolve the cascade, compute specificity winners, or decide inheritance — it just builds a structural tree of every rule exactly as written, selectors and all. The actual winner-picking (specificity comparison, source order, !important, cascade layers) happens later, during the style computation step (its own module shortly), applied against this already-built CSSOM combined with the DOM. This separation is also exactly why cascade layers and media queries can be represented directly inside the CSSOM as structural nodes, rather than needing to be evaluated during parsing itself.

CSS parsing carries no error-recovery drama the way HTML's does, for a simpler underlying reason: an unrecognized property or an invalid value is trivial to handle — the parser just discards that one declaration and moves on to the next, with no ambiguity about how to "recover" the way a mismatched HTML tag creates. This is exactly why browsers can ship experimental or vendor-specific CSS properties, and why using a property a given browser doesn't support fails silently and safely rather than breaking the rest of the stylesheet.

The consequence that actually matters for real performance, already stated as a flat rule in the HTML guide's performance module, finally gets its full explanation here: CSS is render-blocking by default. The browser deliberately withholds the very first paint until it has processed every stylesheet it currently knows about, specifically to avoid a visible "flash" where unstyled content briefly renders and then jumps once real styles apply a moment later. <link rel="preload"> and resource hints (from the CSS guide's performance module) don't remove this blocking behavior — they only make the required stylesheet arrive sooner, shrinking the delay rather than eliminating the underlying constraint.

  • CSS parsing builds the CSSOM, a separate tree from the DOM, structurally mirroring every rule as written.
  • The cascade (specificity, source order, layers) is resolved later, during style computation — not during parsing itself.
  • CSS is render-blocking by design, specifically to prevent a flash of unstyled content — not an accidental limitation.

With both the DOM and the CSSOM built, the browser walks the DOM tree and, for every single node, computes its final, fully-resolved computed style — every CSS property that applies to it, after the cascade has picked a winner among every competing rule, after inheritance has filled in anything not explicitly set, and after relative values like em, %, or var() have been resolved against context. This is the exact value getComputedStyle() returns when called from JavaScript, a method covered in full in this guide's CSSOM-bridge module.

The DOM and the computed styles are then combined into a distinct structure called the render tree — and this is the first point in the whole pipeline where DOM nodes can be genuinely excluded rather than merely hidden. A node with display: none (from the CSS guide's display module) is left out of the render tree entirely — it gets no box, no layout, no paint, nothing — while a node styled with visibility: hidden still gets a full box in the render tree, reserving its layout space, just with nothing actually painted into it. This single distinction is the deep, structural reason those two properties behave so differently, beyond the flat rule stated back in the CSS guide.

::before and ::after pseudo-elements (also from the CSS guide) genuinely enter the render tree as real boxes at this exact stage, generated fresh from their content property — despite never existing as actual nodes anywhere in the DOM tree itself, which is exactly why document.querySelectorAll('*') from JavaScript will never find one: the DOM and the render tree are related but are not the same tree, and JavaScript's DOM APIs only ever see the former.

  • Computed style resolves the cascade, inheritance, and relative units into one final value per property, per element.
  • The render tree combines the DOM with computed styles — display: none nodes are excluded entirely; visibility: hidden nodes still get a box.
  • ::before/::after exist only in the render tree, never in the DOM — invisible to querySelector and friends.

The render tree knows what should appear and roughly what it should look like, but not yet where, or exactly how large. Layout — often still called reflow, its older name — is the step that walks the render tree and computes the exact pixel position and size of every single box: this is the stage where the CSS guide's box model, flexbox, and grid algorithms actually execute as real, concrete geometry, turning declarative rules like flex: 1 or grid-template-columns: repeat(auto-fit, minmax(200px, 1fr)) into one specific, final rectangle per element.

Layout is one of the most expensive operations in the entire pipeline, because it's inherently relational rather than local: changing one element's width can shift its siblings, which can shift its parent's height, which can shift everything after it on the page. For this reason, an engine can rarely re-lay-out just the one element that changed — a change often forces recomputation across a meaningful portion of the tree, sometimes the whole page. This single fact is the actual mechanical justification behind "layout thrashing," a term used but not fully derived in the CSS and JavaScript performance modules — it happens when JavaScript alternates writing a style and then immediately reading a geometric property (like offsetHeight or getBoundingClientRect()) in a tight loop.

Reading a geometric property normally uses whatever layout the browser last computed — cheap. But if JavaScript has just written a style that could plausibly have changed the geometry, the browser can no longer trust its last layout, so it's forced to run an entire synchronous layout pass immediately, right there in the middle of your script, purely to answer that one read accurately — a "forced synchronous layout." Interleaving writes and reads, as in the first example below, forces this expensive recomputation on every single iteration; batching all reads before all writes, as in the second, allows one single layout pass to answer every read at once.

// BAD: forces a fresh, synchronous layout on every single iteration boxes.forEach(box => { box.style.width = box.offsetWidth + 10 + "px"; // write console.log(box.offsetHeight); // read — forces layout NOW }); // GOOD: all reads happen first, then all writes — one layout total const heights = boxes.map(box => box.offsetHeight); // read, read, read boxes.forEach((box, i) => { box.style.width = heights[i] + 10 + "px"; // write, write, write });
  • Layout computes the exact position and size of every box — where the box model, flexbox, and grid algorithms actually execute.
  • Layout is relational, not local — one change can force recomputation across much of the tree.
  • Interleaving style writes with geometry reads forces a synchronous layout on every iteration; batching reads before writes avoids it.
This is the real, underlying mechanism behind "layout thrashing" — a term used in earlier guides without fully explaining why alternating reads and writes is specifically what's expensive.

With exact geometry now known, paint turns each box into actual drawing instructions — fill this rectangle with this color, draw this text, apply this shadow — for every visible pixel. Rather than painting the entire page as one single flat image, the browser can split parts of the page into separate layers, promoting an element onto its own layer when it has a good reason to expect that element will change independently and often — a position: fixed header, an element with a CSS transform or opacity transition, or one explicitly hinted with will-change, exactly as covered in the CSS guide's performance module.

Layers matter because of what happens next: a separate compositor thread — distinct from the main thread that ran layout and most of paint — takes these independently-painted layers and combines them into the final on-screen image, and critically, it can do this combination work on the GPU without going back to the main thread at all. This is the complete, concrete answer to why transform and opacity are so much cheaper to animate than top/left/width: animating a transform or opacity on its own layer only requires the compositor thread to re-combine already-painted layers in a new position or with new transparency — no new layout, often no new paint at all — while animating top or width changes the actual geometry, forcing the full and expensive layout → paint → composite sequence to run again, on the main thread, every single frame.

The full rendering pipeline, start to finish. A transform/opacity animation can often skip straight from Style to Composite.
  • Paint converts sized-and-positioned boxes into drawing instructions, potentially split across independent layers.
  • A separate compositor thread combines layers on the GPU, without involving the main thread.
  • This is the full mechanical reason transform/opacity can skip layout and paint entirely, while top/width cannot.

The JavaScript guide treated console.log and arrow functions as things you simply write; this module opens up what actually happens to that text between the moment it leaves your editor and the moment it executes. A JavaScript engine — V8 in Chrome and Node.js, SpiderMonkey in Firefox — is itself a small pipeline, mirroring the same "parse, then process" shape already seen twice in this guide for HTML and CSS.

First, a parser tokenizes and parses your source text into an AST (Abstract Syntax Tree) — a structural tree representation of your code's actual grammar: this expression is a function call, this is a binary addition, this is a variable declaration. From there, rather than interpreting that tree directly (which would be relatively slow), modern engines compile it down to a compact bytecode — V8 calls its bytecode interpreter Ignition — and execute that instead, already meaningfully faster than walking the raw AST on every single execution.

The genuinely clever part, and the real reason JavaScript performs competitively with far more traditionally "compiled" languages despite feeling like a casually interpreted scripting language, is the JIT (Just-In-Time) compiler — V8's is called TurboFan. While your bytecode runs, the engine quietly watches which functions get called repeatedly and, crucially, what shapes of data they're consistently called with — a function repeatedly called with plain objects that always have the same properties, in the same order, is an excellent optimization candidate. Once a function is identified as "hot" in this way, the JIT compiles it directly to genuine machine code, tailored to those specific observed shapes, entirely bypassing the bytecode interpreter for future calls. If that same function later gets called with a differently-shaped object than the JIT optimized for, the engine "deoptimizes," discarding the fast machine code and falling back to the safer, general bytecode path — a real, measurable performance cliff, and the concrete engineering reason a piece of advice sometimes offered for hot code paths is to keep object shapes consistent (the same properties, added in the same order, on every instance) rather than adding or removing properties dynamically after creation.

This entire process — parse, generate bytecode, execute, watch, optimize, occasionally deoptimize — happens automatically and invisibly, but it is the concrete reason a first call to a function is typically slower than the hundredth, and it's why genuinely reliable JavaScript performance measurement requires "warming up" the code being measured rather than trusting a single cold run.

  • A JS engine parses source into an AST, compiles that to bytecode, and executes the bytecode — the same parse-then-process shape as HTML and CSS.
  • A JIT compiler (TurboFan in V8) promotes frequently-run, consistently-shaped code to real machine code for a large speedup.
  • A function later called with an inconsistently-shaped object can be "deoptimized" back to the slower path — a real, measurable cliff.

JavaScript's memory splits into two genuinely different regions, and understanding both explains exactly why the closures topic in the JavaScript guide works the way it does. The call stack holds function calls themselves — each call pushes a new "frame" containing its local variables and where to return to when it finishes; the frame is popped and its memory reclaimed immediately once the function returns. This stack is also exactly what a "stack trace" in an error actually traces, and exactly what "stack overflow" means literally: too many nested calls (commonly uncontrolled recursion) push more frames than the fixed stack space allows.

The heap is a much larger, less structured region where objects, arrays, and functions themselves actually live — anything whose size isn't known in advance or that needs to outlive the specific function call that created it. This is precisely where closures come from, mechanically: when the JavaScript guide's makeCounter() example returns an inner function that still references count, that count variable cannot live on the stack, since the stack frame for makeCounter() itself is popped the moment it returns — so the engine allocates it on the heap instead, and the returned function keeps a live reference to that heap location for as long as the function itself exists.

Garbage collection is the process that reclaims heap memory automatically, and modern engines use a "mark and sweep" strategy at heart: periodically pause, walk every reachable reference starting from known roots (global variables, currently-executing call stacks), mark everything genuinely still reachable, then free everything left unmarked. This is the precise mechanical definition of a "memory leak" from the JavaScript guide's performance module: an object is not leaked because it's large or old, but specifically because some reference chain — often a forgotten event listener or an active setInterval — still connects it back to a root, keeping it perpetually "reachable" and therefore never eligible for collection, even though nothing in the program will ever meaningfully use it again.

function makeCounter() { let count = 0; // lives on the heap — referenced by the closure below return function increment() { count++; // reads/writes the heap-allocated 'count' return count; }; } // makeCounter's own stack frame is popped here — // but 'count' survives, because the heap keeps it alive
  • The call stack holds function frames, popped immediately on return; the heap holds objects and closed-over variables that must outlive a single call.
  • A closure's captured variables physically live on the heap — that's the mechanical reason they survive after the outer function returns.
  • Garbage collection frees heap memory nothing can still reach — a leak is specifically a lingering reference chain, not an object being simply "old" or "large."

The JavaScript guide's advanced tier explained microtasks fully draining before the next macrotask runs, and proved it with a setTimeout-versus-Promise ordering example. This module places that exact mechanism inside the bigger picture this guide has been building: the event loop isn't a JavaScript-only abstraction running in isolation — it's the same main thread from this guide's Part I, and the browser's own rendering work is interleaved into that identical loop, on genuinely equal footing with your callbacks.

One loop iteration: run a task → drain the entire microtask queue → possibly run rendering steps → repeat.

Concretely, each pass of the loop looks roughly like this: run one task from the task queue (a setTimeout callback, a click handler) to completion; then fully drain the microtask queue — every promise callback, including any new ones added while draining; then, if the browser judges it's a good moment (typically once per frame, roughly every 16.7 milliseconds for a 60Hz screen), run the rendering steps covered across this guide's whole second part — recalculate style, run layout, paint, composite; then go back and pull the next task. This is exactly why a single JavaScript task that runs for hundreds of milliseconds — a large synchronous loop, an expensive computation with no await anywhere inside it — visibly freezes the page: rendering literally cannot run until that task finishes and control returns to the loop, because they share the exact same thread, taking turns rather than running concurrently.

Two APIs exist specifically to cooperate with this rhythm rather than fight it. requestAnimationFrame(callback) schedules a callback to run right before the browser's next paint — the correct, purpose-built tool for any JavaScript-driven visual animation, since it guarantees your code runs at exactly the moment it's actually useful, and the browser will skip calling it altogether for a tab that isn't currently visible, saving battery for free. requestIdleCallback(callback) schedules low-priority work to run only during genuine idle gaps in the loop, after higher-priority tasks and rendering have already had their turn — well suited to analytics reporting or background data prefetching that shouldn't be allowed to compete with anything the user can actually perceive.

  • Rendering steps (style, layout, paint) are interleaved into the exact same event loop as your JavaScript tasks — not a separate process.
  • A long-running synchronous JavaScript task blocks rendering entirely, because they share one thread and take turns.
  • requestAnimationFrame and requestIdleCallback exist to cooperate with this rhythm for animation and low-priority work respectively.

Every earlier module in this guide has referred to "the DOM" as the tree structure HTML parses into. This module makes the actual bridge explicit: the DOM is not just a rendering-engine-internal data structure — it is directly, live, exposed to JavaScript as real, ordinary objects, through exactly the API surface the JavaScript guide's DOM module introduced (document.querySelector, .textContent, .classList, and the rest). There is no serialization, no message-passing, no copying involved in an ordinary DOM read or write from your own page's script — your JavaScript variable is a genuine reference into the browser's actual live tree, the exact same tree the rendering pipeline reads from.

This is precisely why DOM collections returned by some methods are described as "live": document.getElementsByClassName(...) returns a collection that automatically reflects later changes to the document, because it isn't a snapshot copy at all — it's a continuously-updated view into the one real, shared tree. querySelectorAll(...), by contrast, deliberately returns a static, one-time snapshot, precisely so that code iterating over its results doesn't have to reason about the list itself shifting mid-loop as the DOM changes underneath it — a deliberate design trade-off between "always current" and "safe and predictable to iterate," not an inconsistency.

Every DOM mutation from JavaScript — setting .textContent, adding a class, appending a new element — has the potential to invalidate some or all of the render tree, style, and layout computed in the earlier modules of this guide's second part, exactly as covered there: the engine doesn't necessarily recompute immediately on every single mutation, since a script often makes several DOM changes in a row before yielding control back to the browser, but by the time the browser actually needs to render the next frame, every one of those pending changes must be fully reconciled. This is the deep reason the CSS and JavaScript guides both recommend batching multiple DOM changes together (via a document fragment, or by changing one class rather than several individual inline styles) rather than triggering many small, separate mutations — from the pipeline's perspective, it isn't really about the number of JavaScript statements you write, but about how much invalidated work accumulates before the browser is next forced to reconcile it, and unnecessarily forcing that reconciliation mid-script (exactly as in the layout-thrashing example from Part II) is the one true performance trap to avoid.

  • DOM reads/writes from your own page's JavaScript are direct references into the browser's real, live tree — not copies or messages.
  • "Live" collections (getElementsByClassName) reflect later changes automatically; querySelectorAll deliberately returns a static snapshot instead.
  • Every mutation can invalidate style/layout — batching changes together, rather than forcing reconciliation mid-script, is the real performance principle underneath.

Just as the DOM bridges HTML to JavaScript, the CSSOM from Part II bridges CSS to JavaScript — through a smaller, more specialized set of APIs than the DOM's, but built on the exact same underlying tree this guide has already covered in depth. element.style.color = 'red' writes directly to that specific element's inline style, taking the highest-specificity path from the CSS guide's cascade module; element.classList.toggle('active') instead changes which CSS rules apply by changing which selectors match, leaving the actual rule resolution to the normal cascade — generally the better approach precisely because it keeps the actual visual decision-making inside your stylesheet rather than scattering inline overrides through your JavaScript.

getComputedStyle(element) is worth understanding at the mechanism level, not just the API level: because it must return the fully-resolved final value — after the cascade, after inheritance, after relative units are resolved against real layout — calling it can force exactly the same "forced synchronous layout" penalty covered in Part II's layout module, if anything about the page has changed since the last layout pass. This is the precise, concrete reason it belongs on the same "expensive if misused" list as offsetHeight and getBoundingClientRect(), despite reading style information rather than obviously geometric information.

CSS custom properties, from the CSS guide's variables module, are the newest and most direct bridge of all: because a custom property is a genuinely live, runtime CSSOM value rather than a compile-time text substitution, element.style.setProperty('--brand-color', 'seagreen') changes the actual CSSOM immediately, and every rule anywhere in the cascade that reads that variable via var() picks up the new value on the very next style recalculation — a live, two-way conversation between JavaScript and CSS that a preprocessor variable, resolved and discarded before the browser ever sees the file, could never support.

// Cheap: just changes which rule matches; the cascade decides the rest card.classList.toggle("is-featured"); // Can force a synchronous layout if styles/DOM changed since the last frame const width = getComputedStyle(card).width; // Live CSSOM write — every var(--brand-color) rule updates immediately document.documentElement.style.setProperty("--brand-color", "seagreen");
  • element.style writes inline styles directly; classList instead changes which cascade rules match — generally the better-separated approach.
  • getComputedStyle() can force the same synchronous-layout penalty as reading offsetHeight, since it must return a fully-resolved value.
  • Custom properties are a genuinely live, two-way bridge — a JS write updates every rule reading that variable on the next style pass.

An event's actual journey starts further back than JavaScript can see: a physical click is first an operating-system-level input event, delivered to the browser process (from Part I) as the process that genuinely owns the window and receives OS input. The browser process determines which renderer process (and which specific frame within it) the click actually landed in, then forwards that information over IPC to the correct renderer's main thread — the exact same main thread already carrying every other responsibility covered throughout this guide.

Once inside the renderer, the browser must determine exactly which DOM element was actually hit, then dispatches the event by walking the DOM tree — and this is the literal, physical mechanism behind "bubbling" from the JavaScript guide's events module: it is not a metaphor. The event genuinely travels down from the document root to the target element first (the rarely-used capturing phase), then back up through every one of that element's ancestors in turn (the bubbling phase most code relies on), calling any matching listener registered at each step along the way. Event delegation works for exactly this reason — a listener on a distant ancestor is guaranteed to eventually be reached by the same event, on its way back up the very same tree.

One detail with real, measurable performance consequences: addEventListener accepts a { passive: true } option specifically for scroll and touch events, and it exists because of exactly the main-thread contention covered in this guide's Part III. Without it, the browser must run your entire event handler and specifically wait to see whether it calls event.preventDefault() before it's safe to proceed with the native scroll — a mandatory delay on every single scroll event. Marking a listener passive is a promise, enforced by the browser, that it will never call preventDefault(), letting the browser start scrolling immediately on the compositor thread from Part II without waiting for your JavaScript to finish running at all.

// Without { passive: true }, the browser must wait for this handler // to finish (and check for preventDefault) before it can scroll. window.addEventListener("scroll", onScroll, { passive: true }); function onScroll() { // Promising not to call event.preventDefault() lets the browser // start scrolling immediately on the compositor thread. }
  • An input event travels OS → browser process → renderer process → main thread, before your JavaScript ever sees it.
  • Bubbling is a literal tree traversal — capturing phase down, then bubbling phase back up — not just a conceptual description.
  • Passive listeners let the browser start scrolling on the compositor thread immediately, without waiting to see if your handler calls preventDefault().

This module exists to consolidate a fact that's been building across this entire guide into one explicit, practical mental model: every visible change to a page costs one of three genuinely different amounts of work, and knowing which one a given change triggers is the actual skill "web performance" mostly reduces to.

A change that affects an element's geometry — its size, its position, or anything that could ripple to a sibling or ancestor's geometry — forces layout (reflow), and then necessarily paint and composite after it, since the pixels are now wrong wherever the geometry changed. This is the most expensive category: changing width, adding or removing a DOM node, changing text content that reflows a paragraph, even just reading offsetHeight at the wrong moment, as covered in Part II.

A change that affects appearance without affecting geometry — a background color, a box-shadow, a border color — skips layout entirely but still forces paint and composite, since the actual pixels genuinely need to be redrawn even though nothing moved or resized.

A change that affects only an already-composited layer's transform or opacity — as covered in Part II's paint module — can skip both layout and paint, going straight to composite: the compositor thread simply recombines already-painted layers in a new position or with new transparency, on the GPU, without the main thread being involved in that specific step at all. This is the complete, three-tier version of a rule stated flatly and without justification in both the CSS and JavaScript guides' performance modules — every animation or frequent visual update should be evaluated against exactly this three-tier scale, and the cheapest tier that achieves the desired effect is the right one to reach for.

  • Geometry changes force layout, then paint, then composite — the most expensive tier.
  • Appearance-only changes (background-color, box-shadow) skip layout but still force paint and composite.
  • Transform/opacity changes on an already-composited layer can skip straight to composite, on the GPU, off the main thread.
When evaluating any animation or frequent visual update, ask which of these three tiers it actually needs — and reach for the cheapest one that achieves the effect.

Before any parsing from Part II can begin, the network process from Part I has real work to do, and each step has a real time cost that compounds with the ones after it. DNS resolution translates a domain name into an IP address. A TCP handshake establishes a reliable connection to that address. For any HTTPS site — effectively all of them today — a TLS handshake then negotiates encryption before a single byte of the actual page is exchanged. Only after all of that does the browser send its HTTP request and start receiving the HTML response — which, as Part II covered, the browser begins parsing incrementally as it streams in, rather than waiting for the download to finish.

A simplified critical rendering path timeline, left to right.

The critical rendering path is the specific, minimal sequence of steps that must complete before the browser can paint anything at all, and this is precisely where the HTML guide's seemingly simple advice about defer/async and the CSS guide's warning that stylesheets are render-blocking finally connect into one coherent story: a <script> with neither attribute pauses HTML parsing outright until it downloads and runs, directly lengthening the critical path; a stylesheet in the head is deliberately render-blocking by design, from Part II's CSS parsing module, because painting before it arrives risks a jarring flash of unstyled content. defer, async, and resource hints like preload/preconnect (also from earlier guides) don't remove any of these fundamental constraints — they change when and in what order the network process fetches things, and whether a given resource is allowed to block parsing, shrinking the critical path's real-world duration without changing what work it fundamentally requires.

Two named performance metrics you'll encounter constantly in real-world tooling map directly onto specific points on this exact timeline: First Contentful Paint (FCP) is the moment the browser paints the very first pixel of real content, sitting right at the end of the pipeline covered across this whole guide's Part II; Largest Contentful Paint (LCP) is the moment the single largest, most prominent element finishes rendering — often an image or a large block of text — and is widely used as the practical proxy for "does this page feel loaded" from an actual visitor's perspective.

  • DNS, TCP, and TLS all complete before the first byte of HTML is even received — each adds real, compounding time.
  • The critical rendering path is the minimal sequence that must finish before first paint — render-blocking CSS and non-deferred scripts both lengthen it directly.
  • FCP and LCP are named checkpoints on this exact timeline, not separate concepts — they mark specific moments in the pipeline this guide has been building.

Every module up to this point describes what happens for one page load. A multi-page application (MPA) is simply a site that runs this entire process — network request, parse, style, layout, paint — again, completely from scratch, every time the visitor follows a link: a full navigation, a fresh HTML document, a fresh DOM, a fresh JavaScript environment with none of the previous page's in-memory state carried over.

A single-page application (SPA) instead loads this whole pipeline exactly once, for an initial shell page, and from then on uses JavaScript to intercept navigation entirely: instead of asking the browser to load a new document, an SPA's own code updates the URL using the History API's pushState, fetches whatever new data the next "page" needs (typically via the fetch API from the JavaScript guide), and directly manipulates the existing DOM — through the exact same DOM bridge covered in Part IV — to reflect the new view, all without the browser process ever tearing down and rebuilding the renderer process's DOM, CSSOM, or JavaScript execution context from Part I.

This distinction is precisely why an SPA can feel meaningfully faster for navigation between views after the first load — it skips the network request, HTML parsing, and full script re-execution entirely for subsequent "pages" — at the direct cost of a heavier, slower initial load, since the browser typically must download a much larger JavaScript bundle upfront (covered in this part's build-tools module) before anything meaningful can even be shown, and at the cost of needing to manually reimplement things a real browser navigation gives an MPA for free: back/forward button behavior, scroll-position restoration, and — most consequentially for the modules that follow — an actual, complete HTML document for a search engine crawler or a visitor with JavaScript disabled or failing to load.

// A minimal SPA-style navigation, without a full page reload function navigateTo(path) { history.pushState({}, "", path); // updates the URL bar renderView(path); // your own code re-renders the DOM directly } window.addEventListener("popstate", () => renderView(location.pathname));
  • An MPA re-runs the entire pipeline from Part I onward on every navigation; an SPA runs it once and then manages views with JavaScript.
  • SPA navigation skips the network request and full re-parse for subsequent views — faster after the first load, heavier before it.
  • An SPA must manually reimplement what real navigation gives for free: back/forward behavior, scroll restoration, and a complete document for crawlers or JS-disabled visitors.

Part IV's DOM-bridge module established that every DOM mutation is a potential trigger for style recalculation and layout. A real application with genuinely complex, frequently-changing UI can easily end up making many small, individually-triggered DOM mutations across a single logical update — and reasoning by hand about exactly which specific mutations are actually necessary, and batching them correctly yourself every time, becomes genuinely difficult to sustain as an application grows. This is the actual, concrete problem frameworks like React were built to solve — not an abstract preference for a particular coding style.

A virtual DOM is a lightweight, plain-JavaScript-object description of what the UI should look like — critically, not a real DOM node at all, just data, carrying none of the weight of an actual DOM element and forcing none of the invalidation covered in Part IV merely by being created or changed. When your application's state changes, the framework builds a brand new virtual DOM tree describing the desired next state, then compares it against the previous virtual DOM tree it kept from last time — a process called reconciliation, or informally "diffing" — to compute the smallest, most efficient set of actual DOM operations that would take the real, live DOM from its current state to the new one.

Reconciliation: comparing two virtual DOM trees to find the smallest real-DOM patch needed.

This buys two genuinely different things at once, both grounded directly in earlier parts of this guide: it lets a developer write code that simply describes the desired end state — "the list should now contain these three items" — rather than manually tracking and issuing individual DOM mutation calls; and it lets the framework batch the resulting real DOM writes together into one consolidated update rather than many separate ones, directly avoiding the kind of repeated, piecemeal invalidation the DOM-bridge module warned about. The virtual DOM itself is not free — building and diffing two trees costs real CPU time — so it's specifically a trade: a framework bets that the cost of diffing in plain, cheap JavaScript objects is reliably smaller than the cost of the DOM operations it can therefore prevent, a bet that generally pays off for complex, frequently-updating UI and matters far less for a mostly-static page.

  • A virtual DOM is a plain-object description of desired UI, carrying none of a real DOM node's weight or invalidation risk.
  • Reconciliation diffs the previous and next virtual trees to compute the smallest real DOM patch actually needed.
  • This is a genuine cost/benefit trade: diffing cheap JS objects to avoid more expensive, repeated real DOM mutation — not a free abstraction.

Every module so far has quietly assumed the HTML arriving over the network is the actual content. That's server-side rendering (SSR): the server computes the real, final markup for the current page — actual product names, actual article text, genuinely present in the HTML response itself — and the browser's Part II pipeline can begin building a meaningful DOM and painting real content immediately, without waiting on any JavaScript to run first.

Client-side rendering (CSR) is the opposite arrangement, and it's how most single-page applications from this part's earlier module actually deliver their initial content: the server sends a nearly empty HTML shell — commonly just a single <div id="root"></div> — and only once the JavaScript bundle has downloaded, parsed (Part III), and executed does it build the real DOM from scratch and insert genuine content, entirely through the DOM bridge covered in Part IV. Applying the critical-rendering-path module directly: CSR's actual content depends on JavaScript finishing execution first, which is precisely why a CSR page's meaningful First Contentful Paint is, by construction, tied to how quickly its JavaScript bundle downloads and runs — not simply how fast the network can deliver bytes.

Hydration is the increasingly common middle path that tries to get the best of both: the server sends fully-rendered, real HTML exactly as in SSR, so the browser can paint genuine content immediately — but a JavaScript framework then runs on the client anyway, walking that already-painted DOM and attaching event listeners and internal state to it, "hydrating" static markup into a fully interactive application without discarding and rebuilding the DOM the server already so carefully produced. The unavoidable trade-off hydration introduces is a real, sometimes visible gap: a visitor can see fully-rendered content and yet have their click on a button do nothing at all, for the brief window between first paint and the moment hydration actually finishes attaching that button's real event listener.

  • SSR sends real, final content in the HTML itself; CSR sends an empty shell and builds everything via JavaScript after the bundle runs.
  • CSR's First Contentful Paint is tied directly to JS download-and-execution time, not just network speed.
  • Hydration combines SSR's immediate real content with client-side JavaScript attaching interactivity afterward — at the cost of a real, sometimes-visible gap between paint and interactivity.

Part I established that heavy computation on the main thread blocks rendering and input handling outright, because they share one thread. A Web Worker is the direct, load-bearing solution: a genuinely separate JavaScript thread, with its own call stack, heap, and event loop entirely independent from the main thread's — capable of running real, sustained CPU-heavy work (parsing a huge dataset, running an image filter, a complex calculation) without ever blocking rendering, scrolling, or a single input event, precisely because it is a different thread altogether, not merely a different task scheduled on the same one.

The deliberate, non-negotiable trade-off: a Web Worker has no access whatsoever to the DOM — it cannot call document.querySelector or touch a single DOM node directly, specifically because the DOM (per Part IV) is not thread-safe, and allowing simultaneous access from two different threads would reopen exactly the class of concurrency bugs the single-threaded design from Part I exists to prevent in the first place. Instead, a worker communicates with the main thread exclusively by passing messages — postMessage(data) to send, a message event listener to receive — an explicit, deliberately limited channel, not a genuinely shared address space.

A Service Worker is a specialized kind of worker with a different job entirely: rather than raw computation, it acts as a scriptable proxy sitting between your page and the network layer from this part's first module, able to intercept every outgoing network request the page makes and decide whether to let it through, serve a cached response instead, or fabricate a response entirely — the exact mechanism behind offline-capable web apps and reliable, fine-grained caching strategies. Distinctively, a service worker's lifecycle is entirely independent of any one page being open at all: it can keep running in the background to handle a push notification or sync data, entirely detached from whether the tab that originally registered it is even still open.

// main.js const worker = new Worker("compute.js"); worker.postMessage({ numbers: bigArray }); worker.onmessage = (event) => console.log("Result:", event.data); // compute.js — runs on a genuinely separate thread; no DOM access at all self.onmessage = (event) => { const total = event.data.numbers.reduce((a, b) => a + b, 0); self.postMessage(total); };
  • A Web Worker is a genuinely separate thread with its own stack, heap, and event loop — capable of heavy computation without blocking the main thread.
  • Workers cannot touch the DOM directly at all — communication happens only through explicit postMessage/message passing.
  • A Service Worker instead proxies network requests, enabling offline support and caching, and can run independently of any open tab.

The JavaScript guide's modules module introduced import/export and mentioned, briefly, that a bundler typically combines files for production — this module explains exactly why that step exists and precisely what it's doing to your code before Part II's HTML/CSS/JS parsing ever sees it.

A real application is commonly written as dozens or hundreds of separate module files, often using syntax the browser cannot parse directly at all — TypeScript's type annotations from the JavaScript guide's TypeScript module, JSX (an HTML-like syntax embedded directly in JavaScript, common in React), or genuinely newer JavaScript syntax than a given visitor's browser supports. A transpiler (Babel is the most common) rewrites that source code into older, more widely-supported JavaScript that today's actual browsers can parse and run, exactly as covered in this guide's engine module — stripping TypeScript's types away entirely, and converting JSX into the underlying plain function calls it actually represents.

A bundler (Vite, webpack, and similar tools) then walks the entire graph of import statements starting from your application's entry point and combines every file that graph touches into a small number of actual output files — because, in practice, a browser making a hundred small, separate network requests for a hundred small modules is measurably slower than making one or a few requests for larger, combined files, directly due to the per-request network overhead covered in this part's first module. Tree-shaking is a related, deliberate optimization performed during this same bundling step: since ES modules declare their exports statically and explicitly (from the JavaScript guide), a bundler can reliably determine which exported functions are never actually imported anywhere in your application and simply exclude that genuinely unused code from the final bundle entirely, rather than shipping it to every visitor unused.

The end result, and the reason this module belongs in this guide at all: everything covered in Part II about HTML parsing, CSS parsing, and JavaScript engine behavior in Part III still applies exactly as described — but it applies to the bundler's transpiled, combined, tree-shaken output, a file that may look meaningfully different from any file you actually wrote by hand. Your authored source code and the bytes the browser's parser actually consumes are, in any real modern application, two genuinely different things connected by this build step.

  • A transpiler rewrites newer syntax (TypeScript, JSX, newer JS) into older, widely-supported JavaScript the browser can actually parse.
  • A bundler combines many small module files into fewer, larger ones — fewer requests, directly reducing the network overhead covered earlier in this part.
  • Tree-shaking excludes genuinely unused exports from the final bundle, relying on ES modules' static, explicit export declarations.

Every module in this guide has deliberately built toward one single, connected story rather than a list of unrelated facts. This module tells that story once, straight through, as a single concrete journey — a visitor clicking a product link on an online store — with each step naming the exact mechanism from earlier in this guide that actually makes it happen. Nothing below is new; the only goal here is to show it all connected, in order.

  1. The click is first an OS-level input event. The browser process receives it, determines which renderer process and frame it landed in, and forwards it over IPC to that renderer's main thread (Part I; Part IV's events module).
  2. For a traditional full navigation, the network process now performs DNS resolution, a TCP handshake, and a TLS handshake before the HTML response even begins arriving (Part V's network module). An SPA intercepting the click instead calls history.pushState and fetches only the data it needs, skipping this step almost entirely (Part V's MPA/SPA module).
  3. Assuming a real navigation: the HTML tokenizer and tree builder construct the DOM incrementally as bytes stream in, while a preload scanner looks ahead for referenced stylesheets, scripts, and images and starts fetching them immediately, in parallel (Part II's HTML parsing module).
  4. CSS arrives and is parsed into the CSSOM — deliberately render-blocking, specifically to avoid a flash of unstyled content (Part II's CSS parsing module).
  5. DOM and CSSOM combine into computed style and the render tree, excluding display: none nodes and materializing ::before/::after as boxes that exist only here, never in the DOM itself (Part II's render tree module).
  6. Layout computes the exact geometry of every visible box — the point where flexbox and grid algorithms become real, final numbers (Part II's layout module).
  7. Paint converts that geometry into drawing instructions, potentially split across layers; the compositor thread combines them into the final image on the GPU — First Contentful Paint happens right here (Part II's paint module; Part V's network module).
  8. Any <script> without defer/async appearing earlier in the document would have paused step 3 entirely to download and run first, directly lengthening every step after it — the full justification behind the HTML guide's script-placement advice (Part II; Part V's critical rendering path module).
  9. Once interactive, JavaScript takes over: event listeners share the exact same main thread that just ran the pipeline above, taking turns with it through the event loop — draining microtasks between tasks, running rendering steps roughly once per frame (Part III's event loop module).
  10. The visitor adds the product to their cart. JavaScript mutates the DOM directly — a live reference into the very tree the renderer reads, not a copy — invalidating style and layout for the affected region (Part IV's DOM bridge module). In a framework-based app, that same mutation flows through a virtual DOM diff first, reconciling down to the smallest real patch before touching the live tree at all (Part V's virtual DOM module).
  11. A price updates through a live CSS custom property write, picked up by every var()-referencing rule on the next style pass; a small animation uses transform rather than changing width, letting it skip straight to composite on the GPU instead of forcing a fresh layout (Part IV's CSSOM bridge and reflow/repaint modules).
  12. Behind the scenes, a service worker may have served a cached shell instantly on the very first request while quietly checking for updates, and a web worker may be recalculating shipping estimates on a genuinely separate thread, so none of this blocks the interaction actually happening on screen (Part V's workers module).

Every sentence above is a direct callback to a mechanism this guide already covered in full. That repetition is the entire point: HTML, CSS, and JavaScript were never three separate subjects running in parallel. They are three inputs into one continuous, physical machine — a specific sequence of processes, threads, trees, and queues — and every rule of thumb stated flatly in the earlier syntax-focused guides in this series ("prefer transform over top," "batch your DOM reads and writes," "put scripts at the bottom, or use defer") was always a description of how to work efficiently with that exact machine, offered before the machine itself had actually been shown.

  • HTML, CSS, and JavaScript feed into one continuous physical machine, not three parallel, independent tracks.

Every term used across this guide, in one place, alphabetically, for quick lookup — nothing here should require looking anywhere else to understand.

AST (Abstract Syntax Tree)
A tree representation of source code's grammatical structure, produced by a parser before an engine compiles or interprets it.
Bundler
A build tool that combines many separate module files into a smaller number of output files, reducing network requests.
Bytecode
A compact, lower-level instruction format a JavaScript engine compiles source code to before execution, faster to run than walking a raw AST.
Call stack
The structure tracking active function calls; each call pushes a frame, popped and reclaimed the moment that function returns.
Composite / Compositor thread
The final pipeline stage that combines painted layers into the on-screen image; performed by a thread separate from the main thread, often on the GPU.
Computed style
The fully-resolved value of every CSS property for an element, after the cascade, inheritance, and unit resolution have all been applied.
Critical rendering path
The minimal sequence of steps — network, parsing, style, layout, paint — that must complete before a browser can paint anything at all.
CSR (Client-Side Rendering)
A rendering strategy where the server sends a near-empty HTML shell and JavaScript builds the real content in the browser after loading.
CSSOM (CSS Object Model)
The tree structure the browser builds by parsing CSS, combined with the DOM to compute style and build the render tree.
DOM (Document Object Model)
The tree structure built by parsing HTML, exposed live to JavaScript — a JS reference to a DOM node is a genuine reference into the browser's real tree.
Event bubbling / capturing
The two literal phases of DOM event dispatch: capturing travels root-to-target first, bubbling then travels target-to-root — the mechanism behind event delegation.
Event delegation
Attaching one listener to a shared ancestor instead of many listeners to individual children, relying on bubbling to still catch every relevant event.
Event loop
The mechanism that repeatedly runs a task, fully drains the microtask queue, and periodically runs rendering steps, all on one shared main thread.
FCP (First Contentful Paint)
The moment the browser paints the first pixel of real content — a specific point on the critical rendering path's timeline.
Garbage collection
The automatic process that frees heap memory no longer reachable from any root reference; a "leak" is a lingering reference chain that prevents this.
GPU process
The browser process responsible for rasterization and compositing, offloading that work to graphics hardware.
Heap
The memory region holding objects, arrays, functions, and closed-over variables that must outlive a single function call.
Hydration
Attaching JavaScript-driven interactivity to already server-rendered HTML, without rebuilding the DOM the server produced.
IPC (Inter-Process Communication)
The controlled channel through which sandboxed browser processes exchange information, since none can reach directly into another's memory.
JIT compiler (Just-In-Time)
Compiles frequently-run, consistently-shaped bytecode directly to machine code for a large speedup, with a real deoptimization penalty if shapes change.
LCP (Largest Contentful Paint)
The moment the largest visible element finishes rendering — a common practical proxy for whether a page feels loaded.
Layer (compositing layer)
An independently painted piece of the page, promoted for elements expected to change often — enables cheap, GPU-only transform/opacity animation.
Layout (Reflow)
The pipeline stage that computes the exact size and position of every box; relational rather than local, and one of the most expensive steps.
Main thread
The single thread inside a renderer process that runs HTML/CSS parsing, layout, most of paint, and all ordinary JavaScript — one thing at a time.
Microtask / microtask queue
Promise callbacks and code resumed by await; the entire microtask queue always drains completely before the next macrotask runs.
MPA (Multi-Page Application)
A site that runs the full navigation pipeline from scratch on every link click, with no state carried over between pages.
Network process
The browser process centralizing DNS, TCP/TLS, HTTP requests, and the shared disk cache for every open tab.
Paint
The stage that converts sized, positioned boxes into actual drawing instructions for pixels.
Passive event listener
A listener registered with { passive: true }, promising never to call preventDefault(), letting the browser scroll immediately without waiting on it.
Preload scanner
A lightweight secondary HTML scan that starts fetching referenced resources before the main parser reaches them.
Reconciliation
A framework's process of diffing a previous and next virtual DOM tree to compute the smallest real DOM patch required.
Render tree
The DOM combined with computed style, excluding display: none nodes and including generated ::before/::after boxes.
Renderer process
The sandboxed, typically per-site process where HTML/CSS parsing, layout, and JavaScript execution actually happen.
Sandboxing
OS-level restriction preventing a renderer process from directly accessing the filesystem or other processes, regardless of what code runs inside it.
Service worker
A worker that proxies network requests for a site, enabling offline support and custom caching, running independently of any open tab.
Site isolation
The policy of giving each site its own renderer process, preventing one site's script from reading another site's memory.
SPA (Single-Page Application)
An app that loads the full pipeline once, then manages subsequent views with JavaScript and the History API instead of full navigations.
SSR (Server-Side Rendering)
A rendering strategy where the server sends complete, final HTML content, letting the browser paint real content without waiting on JavaScript.
Task / task queue (macrotask)
Discrete units of work like a setTimeout callback or an input event; one runs per event loop iteration, after which microtasks fully drain.
Tokenization
The first parsing stage, converting a character stream into meaningful tokens, shared conceptually by HTML, CSS, and JavaScript parsing.
Transpiler
A tool that rewrites newer or non-standard syntax (TypeScript, JSX) into older JavaScript a browser can parse directly.
Tree-shaking
A bundler optimization that excludes exported code nothing ever actually imports, relying on ES modules' static export declarations.
Virtual DOM
A lightweight plain-object description of desired UI, diffed against its previous version to batch real DOM updates efficiently.
Web worker
A genuinely separate JavaScript thread with its own stack, heap, and event loop, unable to touch the DOM, communicating only via message passing.
