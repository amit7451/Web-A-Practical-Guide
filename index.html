HTML stands for HyperText Markup Language. Markup is the operative word: HTML describes the structure and meaning of content — this is a heading, this is a list, this is a link — and leaves how it looks to CSS and how it behaves to JavaScript. Confusing these jobs is the single most common beginner mistake: reaching for a bigger heading tag because you want bigger text, instead of using CSS to make text bigger and picking the heading tag because it is a heading.

The web's original idea, from Tim Berners-Lee's work at CERN in 1991, was "hypertext": documents that link to other documents. HTML has grown enormously since — audio, video, forms, offline storage, custom components — but linking is still baked into its name and its most important tag, <a>.

HTML today isn't a fixed numbered specification you finish reading once. It's maintained as a "living standard" by the WHATWG, updated continuously as browsers add capabilities. That's why this guide is organized by what you need to know, not by version number.

What the browser does with it

When a browser receives HTML, it parses the text into a tree of objects called the DOM (Document Object Model). CSS then paints that tree, and JavaScript can read and change it. Everything else in web development sits on top of this one idea.

<!DOCTYPE html> <html lang="en"> <head> <meta charset="UTF-8"> <title>My First Page</title> </head> <body> <h1>Hello, web</h1> <p>This paragraph is structure. Its color is CSS's job.</p> </body> </html>
  • HTML describes structure and meaning; CSS handles appearance; JavaScript handles behavior.
  • Browsers parse your markup into a DOM tree — that tree is what CSS styles and JavaScript touches.
  • HTML is a continuously updated "living standard," not a version you finish learning once.
  • Never choose a tag purely for its default visual size or style — choose it for what it means.
Open any website, right-click, and choose "View Page Source" (or press Ctrl+U / Cmd+Option+U). Reading real markup from sites you use daily teaches you faster than any tutorial.

Every HTML page follows the same skeleton, and each piece has a specific job.

<!DOCTYPE html> must be the very first line. It tells the browser to render the page in modern "standards mode" rather than guessing based on old, inconsistent quirks from the 1990s. It isn't a tag with a closing pair — it's a one-time instruction.

The <html> element wraps everything and should carry a lang attribute, such as lang="en". This one small attribute lets screen readers choose the correct pronunciation rules and lets browsers offer translation — it's an accessibility feature disguised as an afterthought.

Inside <html> there are exactly two children: <head> and <body>. The head holds information about the page — metadata, the title, links to stylesheets — none of which is directly visible. The body holds everything a visitor actually sees.

Two meta tags you always want

<meta charset="UTF-8"> should be the first thing inside <head>. It tells the browser how to decode the bytes of your file into characters, so accented letters, emoji, and non-Latin scripts render correctly. <meta name="viewport" content="width=device-width, initial-scale=1.0"> tells mobile browsers to render at the phone's actual width instead of pretending to be a 980px-wide desktop page and zooming out — without it, your responsive CSS won't behave on phones at all.

<!DOCTYPE html> <html lang="en"> <head> <meta charset="UTF-8"> <meta name="viewport" content="width=device-width, initial-scale=1.0"> <title>Page Title</title> <link rel="stylesheet" href="styles.css"> </head> <body> <!-- visible content goes here --> </body> </html>
  • <!DOCTYPE html> comes first and switches on standards mode.
  • <html lang="en"> helps screen readers and translation tools — set it correctly.
  • <head> holds metadata; <body> holds what visitors see.
  • Charset and viewport meta tags belong in every page you ship.
Skipping the viewport meta tag is the most common reason a page that "looks fine" on a laptop looks tiny and zoomed-out on a phone.

HTML gives you six heading levels, <h1> through <h6>. They exist to describe an outline of your document, the same way a book's chapter and section titles do — not to pick a font size. Screen readers let users jump between headings the way you'd flip through a table of contents, which only works if the levels genuinely nest: an <h3> should sit under an <h2>, which sits under the page's single <h1>.

Skipping a level — going from <h1> straight to <h3> because it "looks right" — breaks that outline for anyone navigating by structure, even though sighted users browsing normally won't notice anything wrong.

Regular text lives in <p> elements. One detail trips up almost every newcomer: browsers collapse whitespace. Line breaks and extra spaces in your HTML source do not create line breaks or spacing on the rendered page — only actual elements and CSS do.

<h1>Backyard Vegetable Gardening</h1> <p>An introduction for first-time growers.</p> <h2>Choosing a Location</h2> <p>Most vegetables need six hours of direct sun.</p> <h3>Testing Your Soil</h3> <p>A simple pH kit will tell you what to amend.</p> <h2>Watering Schedules</h2> <p>Deep, infrequent watering beats a daily sprinkle.</p>
  • Headings encode document structure, not font size — style size with CSS instead.
  • Don't skip heading levels; assistive technology relies on the nesting being real.
  • Most pages use one <h1> for the main topic of that page.
  • Whitespace and line breaks in your source are collapsed by the browser.

HTML has pairs of tags that look similar but mean different things. <strong> marks text as genuinely important — screen readers may change their tone for it — while <b> just makes text bold with no claim about importance. Likewise <em> marks stressed emphasis (changing which word carries meaning in a sentence), while <i> is purely a visual italic, appropriate for things like foreign phrases or the names of ships, which are conventionally italicized without being "emphasized."

A few more inline tags worth knowing: <small> for fine print or side comments, <mark> for highlighting text that's relevant right now (like a search match), <abbr title="..."> for abbreviations — the title gives the full expansion — and <sub>/<sup> for subscript and superscript, useful in chemical formulas or footnote markers.

<br> forces a single line break and <hr> marks a thematic break between sections of content. Neither is a layout tool — reach for CSS margin and spacing instead of stacks of <br> tags.

<p> <strong>Warning:</strong> the <em>first</em> step is irreversible. See <abbr title="Frequently Asked Questions">FAQ</abbr> for details. </p> <p>The compound is H<sub>2</sub>O, discovered in <mark>1783</mark>.</p>
  • <strong>/<em> carry meaning; <b>/<i> are purely visual.
  • <abbr title="..."> gives assistive tech and hover users the full expansion.
  • <br> and <hr> are not spacing or decoration tools — use CSS for layout.

The anchor tag, <a href="...">, is HTML's namesake feature. The href can be absolute (https://example.com/page), relative to the current page (about.html or ../images/logo.png), or a jump to a section on the same page using an id: <a href="#pricing"> scrolls to whichever element has id="pricing".

target="_blank" opens a link in a new tab. When you use it, also add rel="noopener noreferrer" — without it, the new page can access window.opener and, in older browsers, silently redirect your original tab to a phishing page. You'll see exactly why this matters in the security topic later in this guide.

Two special schemes turn a link into an action: mailto: opens the visitor's email client with an address pre-filled, and tel: dials a number on devices that can place calls.

<a href="/about.html">About us</a> <a href="https://example.com" target="_blank" rel="noopener noreferrer">External site</a> <a href="mailto:hello@example.com">Email us</a> <a href="tel:+15551234567">Call us</a> <a href="#section-2">Jump to Section 2</a> <h2 id="section-2">Section 2</h2>
  • Relative paths point to files near the current page; absolute paths point anywhere on the web.
  • Always pair target="_blank" with rel="noopener noreferrer".
  • mailto: and tel: turn a link into a real-world action.
If a click should trigger app behavior rather than navigate to a URL — like opening a modal — use a <button>, not an <a href="#">. A fake link confuses keyboard and screen reader users who expect links to navigate.

<img src="..." alt="..."> is a void element — it never has a closing tag or content. The alt attribute is not optional decoration: it's read aloud by screen readers, displayed if the image fails to load, and used by search engines. Write it as you would describe the image to someone on the phone. If an image is purely decorative and adds no information — a background flourish — give it an empty alt="" so assistive technology skips over it entirely, rather than omitting alt, which some screen readers announce as the filename instead.

Always set width and height (or the equivalent CSS aspect-ratio). The browser uses them to reserve space for the image before it finishes downloading, which prevents the rest of the page from jumping around as images pop in — a real, measured metric called Cumulative Layout Shift.

When an image needs a caption, wrap both in <figure> with a <figcaption> inside. This semantically ties the caption to the image as one unit, rather than leaving them as two unrelated pieces of text.

<figure> <img src="harvest.jpg" alt="Wicker basket of freshly picked tomatoes and basil" width="640" height="427"> <figcaption>First tomato harvest of the season, late July.</figcaption> </figure> <img src="divider-flourish.svg" alt="" width="200" height="12">
  • alt is required — describe meaningfully, or use alt="" for purely decorative images.
  • width/height prevent layout shift while images load.
  • <figure>/<figcaption> groups an image with its caption as one semantic unit.

Use <ul> (unordered list) when items have no inherent ranking — ingredients, features, links in a menu. Use <ol> (ordered list) when sequence carries meaning — recipe steps, race results, instructions where order matters. Each item, in either case, is an <li>.

A less common but genuinely useful third type is the description list: <dl> wraps pairs of <dt> (term) and <dd> (its description) — perfect for glossaries, FAQs, or metadata like a spec sheet.

Lists can nest: placing a full <ul> or <ol> inside an <li> creates a sub-list, which is how multi-level outlines and navigation menus with sub-items are built.

<ol> <li>Preheat the oven to 220°C.</li> <li>Toss the vegetables in oil and salt.</li> <li>Roast for 25 minutes, turning once.</li> </ol> <dl> <dt>HTML</dt> <dd>Describes the structure of a web page.</dd> <dt>CSS</dt> <dd>Describes how that structure should look.</dd> </dl>
  • <ul> for unordered items, <ol> when sequence matters.
  • <dl>/<dt>/<dd> handles term–description pairs like glossaries and FAQs.
  • Lists can nest inside a parent <li> to build sub-lists.

Tables exist for genuinely grid-shaped data — pricing plans, schedules, comparison specs — where rows and columns both carry meaning. Before CSS matured, developers abused tables to lay out entire pages; that technique is obsolete and actively harmful to accessibility today, since screen readers announce table structure and a layout table announces confusing, meaningless "row 1 of 40" noise.

The structure: <table> wraps rows (<tr>), which contain header cells (<th>) or data cells (<td>). Grouping rows into <thead>, <tbody>, and optionally <tfoot> lets browsers keep the header visible while a long table scrolls or prints, and tells assistive technology exactly which row is the header.

A <caption>, placed right after the opening <table> tag, gives the whole table an accessible title — the equivalent of a figure caption, but for data.

<table> <caption>Quarterly rainfall (mm)</caption> <thead> <tr><th>City</th><th>Q1</th><th>Q2</th></tr> </thead> <tbody> <tr><td>Mumbai</td><td>12</td><td>480</td></tr> <tr><td>Delhi</td><td>6</td><td>210</td></tr> </tbody> </table>
  • Tables are for tabular data, never for page layout.
  • <th> marks header cells; pair it with <thead>/<tbody> for structure.
  • <caption> gives the table an accessible title.

A <form> wraps a set of input controls. Its action attribute says where the data goes, and method says how: GET appends data to the URL and suits read-like requests such as a search box, while POST sends data in the request body and suits anything that changes state, like creating an account.

Every input needs a real <label>, connected either by wrapping the input or by matching a for attribute to the input's id. A placeholder is not a substitute — it vanishes the moment someone starts typing and isn't dependably announced by every screen reader. Clicking a label should focus or toggle its input; that only happens with a real association.

Inside a form, a plain <button> defaults to type="submit" — including buttons you intended for something else, like "Cancel." That default causes a classic bug: a cancel button that unexpectedly submits the form. Set type="button" explicitly on anything that shouldn't submit.

<form action="/subscribe" method="post"> <label for="email">Email address</label> <input type="email" id="email" name="email" required> <button type="submit">Subscribe</button> <button type="button" onclick="closeForm()">Cancel</button> </form>
  • GET for read-like requests, POST for anything that changes data.
  • Every input needs a real, connected <label> — a placeholder is not enough.
  • Buttons inside a form default to type="submit"; say type="button" otherwise.
A "Cancel" or "Delete row" button inside a <form> that's missing type="button" will silently submit the entire form when clicked — one of the most common real-world form bugs.

A handful of attributes work on nearly every element. id gives a single element a unique name on the page — used for anchor links, label associations, and as a hook for CSS or JavaScript. Unlike id, class can repeat across many elements and can hold several space-separated values, making it the right tool for reusable styling hooks.

style lets you write inline CSS directly on an element, but reach for it sparingly — mixing structure and presentation defeats much of the reason HTML and CSS are separate languages in the first place. title adds a tooltip, but support across assistive technology is inconsistent, so never put essential information only in a title.

data-* attributes let you attach custom data for JavaScript to read — data-user-id="42", for instance — without inventing non-standard attributes. The boolean hidden attribute removes an element from rendering entirely.

Some elements are "void": they carry no closing tag and no content, because they can't have children — <br>, <img>, <input>, <hr>, <meta>, and <link> among them.

Finally, <!-- comments --> are stripped before anything renders on screen, but they still travel to every visitor inside your page's source. Never put secrets, internal notes, or anything sensitive in one.

<section id="pricing" class="panel panel--highlighted" data-plan="pro"> <!-- TODO: swap in final copy before launch --> <p title="Billed annually">$12/month</p> </section>
  • id is unique per page; class can repeat and hold multiple values.
  • Prefer real CSS files over inline style where you can.
  • data-* attributes are the standard way to attach custom data for scripts.
  • Comments are invisible on the page but fully visible in "View Source."

Before HTML5, every section of a page was a generically named <div>, and developers relied on id="header" or class="nav" to fake meaning that the browser itself couldn't see. HTML5 added elements that describe a section's role directly: <header>, <nav>, <main>, <article>, <section>, <aside>, and <footer>.

<header> holds introductory content — it can appear once for the whole page and again inside an individual <article>. <nav> wraps major navigation blocks, not every group of links. <main> should appear exactly once per page and wrap the primary content, letting screen reader users jump straight past repeated navigation. <footer> mirrors <header> for closing or meta content, and <address> specifically marks contact information for the nearest article or page.

The trickiest distinction is <article> versus <section>. Ask: "could this be pulled out and make sense on its own, syndicated elsewhere?" — a blog post, a product card, a forum comment — that's an <article>. A <section> is a thematic chunk of a larger whole, usually introduced by its own heading, that doesn't stand alone the same way. <div> and <span> still matter as the meaning-neutral fallback for purely visual grouping when no semantic element actually fits — reaching for them isn't wrong, it's just a last resort rather than a default.

<body> <header> <h1>Daily Bread Bakery</h1> <nav><a href="/menu">Menu</a> <a href="/visit">Visit</a></nav> </header> <main> <article> <h2>Sourdough, back in stock</h2> <p>Our 48-hour ferment loaf returns Thursday.</p> </article> <aside> <h2>Opening hours</h2> <p>Tue–Sun, 7am–3pm</p> </aside> </main> <footer> <address>Contact: <a href="mailto:hello@dailybread.example">hello@dailybread.example</a></address> </footer> </body>
  • Semantic elements describe a section's role, not just its grouping.
  • Use exactly one <main> per page, wrapping the primary content.
  • <article> should make sense standing alone; <section> is a themed part of a larger whole.
  • <div>/<span> remain valid as a last-resort, meaning-neutral wrapper.
Screen reader users often jump between landmarks (header, nav, main, footer) the way sighted users scan a page visually. Getting these elements right is a large accessibility win for almost no extra effort.

The type attribute on <input> is more powerful than it looks. type="email" and type="tel" summon the right mobile keyboard layout; type="number", type="date", type="range", and type="color" give you a purpose-built native control for free, with no JavaScript; type="checkbox" and type="radio" handle multi-select and single-select choices respectively — radios sharing the same name become mutually exclusive automatically.

<fieldset> groups related controls — most usefully a set of radio buttons or checkboxes — and its first child, <legend>, gives that whole group an accessible label, announced by screen readers as you enter the group.

<select> with nested <option> elements builds a dropdown restricted to exactly the choices you list; <optgroup label="..."> visually and semantically clusters related options. A <textarea> handles multi-line freeform text — size it with CSS rather than the legacy rows/cols attributes where you can. <datalist>, linked to an input via matching list/id, offers autocomplete suggestions while still letting the visitor type anything — unlike <select>, it never restricts the final value. <output> displays a computed result, linkable to its source inputs with a for attribute, typically updated by a script listening for input changes.

<fieldset> <legend>Preferred contact method</legend> <label><input type="radio" name="contact" value="email" checked> Email</label> <label><input type="radio" name="contact" value="phone"> Phone</label> </fieldset> <label for="city">City</label> <input type="text" id="city" list="city-options"> <datalist id="city-options"> <option value="Mumbai"> <option value="Delhi"> <option value="Bengaluru"> </datalist>
  • Choosing the closest type gets you the right keyboard and built-in control for free.
  • <fieldset>/<legend> gives a whole group of related controls one accessible label.
  • <datalist> suggests options but still allows free text; <select> restricts to the list.
type="tel" deliberately accepts any text, since phone formats vary worldwide — add a pattern attribute yourself if you need to enforce a specific format.

Browsers can validate a surprising amount for free, purely through attributes: required blocks submission on an empty field, minlength/maxlength bound text length, min/max bound numeric or date values, pattern takes a regular expression the value must match, and step controls the increment allowed for numbers. This is the Constraint Validation API, and it comes with matching CSS hooks — :valid, :invalid, :required, :optional — so you can style a field red or green purely based on its current state, no JavaScript required.

If you need fully custom validation logic or UI, add novalidate to the <form> to switch off the browser's built-in checks and handle everything yourself in script.

Whatever you do on the client, it is never a substitute for validating again on the server. Client-side checks are for user experience — instant feedback without a round trip — while server-side checks are for security, since anyone can submit a request directly and skip your HTML and JavaScript entirely.

<label for="username">Username</label> <input type="text" id="username" required minlength="3" maxlength="20" pattern="[a-zA-Z0-9_]+" title="Letters, numbers, and underscores only"> <label for="qty">Quantity</label> <input type="number" id="qty" min="1" max="10" step="1" value="1">
  • required, pattern, min/max, and step give validation with zero JavaScript.
  • :valid/:invalid let CSS style a field based on its current validity.
  • novalidate on the form opts out when you need fully custom validation.
Trusting client-side validation alone is a real security bug, not just sloppiness — always re-check every rule on the server, since the browser's checks are trivially bypassed by anyone sending requests directly.

<video> and <audio> embed media with a built-in player when you add the controls attribute — skip it only if you're building fully custom playback controls in JavaScript. Nested <source> elements let you offer the same media in several formats; the browser tries each in order and plays the first one it can decode, which matters because format support still varies across browsers.

A <track kind="captions" src="captions.vtt" srclang="en" label="English"> inside a <video> adds captions or subtitles from a separate file — essential for anyone who is deaf or hard of hearing, watching without sound, or simply searching within the video's text. The poster attribute sets a still preview image shown before playback starts.

Browsers block video with sound from autoplaying — if you need autoplay (for a silent background loop, say), pair it with muted or it simply won't play. Any content placed between the opening and closing tags acts as a fallback, shown only if the browser can't play the element at all.

<video controls poster="preview.jpg" width="640" height="360"> <source src="talk.webm" type="video/webm"> <source src="talk.mp4" type="video/mp4"> <track kind="captions" src="talk-en.vtt" srclang="en" label="English" default> Your browser doesn't support embedded video. <a href="talk.mp4">Download the video</a> instead. </video>
  • Include controls unless you're replacing them with your own custom UI.
  • <track> supplies captions — treat it as a requirement, not an extra.
  • Autoplaying video must also be muted, or browsers will block it.

<iframe src="..."> embeds an entire separate HTML document inside your page — used for maps, embedded videos, checkout widgets, or ads. Because an iframe runs someone else's code alongside yours, treat every one as a security boundary rather than a neutral picture frame.

The sandbox attribute strips capabilities from the embedded page by default and re-grants only what you list: sandbox="allow-scripts" permits scripts but still blocks forms, popups, and top-level navigation unless you add those tokens too. An empty sandbox="" locks everything down as tightly as possible. loading="lazy" defers offscreen iframes from loading until they're about to scroll into view, the same as it does for images.

<object> and <embed> are older, now-niche ways to embed plugin content like PDFs; for the vast majority of modern uses, an <iframe> for documents or the <video>/<audio> elements you already know cover the job better.

<iframe src="https://maps.example.com/embed?q=CERN" title="Map showing the location of CERN" loading="lazy" sandbox="allow-scripts allow-same-origin" width="600" height="360"> </iframe>
  • Treat every <iframe> as a security boundary, not just a layout tool.
  • sandbox strips capabilities by default; add only the tokens you actually need.
  • Give every iframe a descriptive title so screen reader users know what it contains.
A missing title means a screen reader announces the frame only as "iframe" — a real title tells visitors what's inside before they enter it.

The <head> carries several tags aimed at search engines and link previews rather than visitors reading the page directly. <meta name="description" content="..."> supplies the summary many search engines show under your title — it doesn't directly affect ranking, but a well-written one affects whether people click. <meta name="robots" content="noindex, nofollow"> asks search engines to leave a page out of results entirely, useful for admin pages or duplicates.

<link rel="canonical" href="..."> tells search engines which URL is the authoritative version when the same content is reachable multiple ways (with and without tracking parameters, for instance), avoiding duplicate-content confusion. A favicon comes from <link rel="icon" href="...">.

Open Graph tags (og:title, og:description, og:image) control how a link looks when shared on social platforms and chat apps; Twitter/X has its own similar set of twitter:* tags for the same purpose. None of this makes content appear that isn't genuinely on the page — it describes what's already there to systems that can't otherwise summarize it well.

<meta name="description" content="Hand-thrown pottery classes in central Pune, weekend and evening slots."> <link rel="canonical" href="https://example.com/classes"> <link rel="icon" href="/favicon.ico"> <meta property="og:title" content="Pottery Classes — Clay & Wheel Studio"> <meta property="og:description" content="Weekend and evening slots, all skill levels."> <meta property="og:image" content="https://example.com/social-card.jpg">
  • Meta description affects click-through from search results, not ranking directly.
  • rel="canonical" resolves duplicate-content confusion across near-identical URLs.
  • Open Graph and Twitter tags control link previews on social platforms and chat apps.

A single fixed-size image is a poor fit for the range of screens visiting your site: too large and it wastes bandwidth on a phone, too small and it looks blurry on a high-density display. srcset lets one <img> list several resolutions of the same picture, and sizes tells the browser how wide the image will actually render at different viewport widths — together the browser picks whichever file makes sense for the visitor's exact screen. This is called "resolution switching," and it keeps the same crop throughout.

When you need a genuinely different crop at different sizes — a tight portrait crop on mobile, a wide landscape crop on desktop — that's "art direction," and it calls for <picture> wrapping several <source media="..." srcset="..."> elements plus a required fallback <img> for browsers that support none of the listed sources.

loading="lazy" on an <img> defers offscreen images until they're about to enter the viewport, which speeds up the initial page load without any JavaScript.

<picture> <source media="(min-width: 800px)" srcset="hero-wide.jpg"> <source media="(max-width: 799px)" srcset="hero-tall.jpg"> <img src="hero-wide.jpg" alt="Potter shaping a bowl on a wheel" loading="lazy" width="1200" height="675"> </picture> <img src="thumb-400.jpg" srcset="thumb-400.jpg 400w, thumb-800.jpg 800w, thumb-1200.jpg 1200w" sizes="(min-width: 600px) 400px, 100vw" alt="Finished ceramic mug">
  • srcset/sizes handle resolution switching — same crop, best-fit size.
  • <picture> handles art direction — genuinely different crops per breakpoint.
  • loading="lazy" defers offscreen images to speed up initial load.

The rel attribute describes the relationship between the current page and a linked one, and several values matter beyond the noopener noreferrer pair you met earlier. rel="noopener" stops a page opened via target="_blank" from getting a JavaScript handle back to your window; rel="noreferrer" goes further and withholds the referrer header entirely, so the destination can't see where the click came from.

rel="nofollow" tells search engines not to pass ranking credit through a link — common practice on user-submitted or paid links. Two more specific variants exist for the same family of cases: rel="sponsored" for paid or advertising links, and rel="ugc" for user-generated content like comments.

The download attribute on a link forces a save-to-disk instead of navigation, and can suggest a filename: <a href="report.pdf" download="Q3-report.pdf">. Separately, <link rel="preload" as="..." href="..."> in the document head — not on an <a> — tells the browser to fetch a resource it will need soon, before it would otherwise discover it.

<a href="https://partner.example" rel="sponsored">Our sponsor</a> <a href="/user/42/comment/9" rel="ugc">See their comment</a> <a href="/invoice.pdf" download="Invoice-2451.pdf">Download invoice</a> <link rel="preload" as="font" href="/fonts/inter.woff2" type="font/woff2" crossorigin>
  • noopener/noreferrer protect your window and its referrer data from a linked page.
  • nofollow/sponsored/ugc tell search engines how to treat a link's authority.
  • download saves a file directly, optionally under a custom filename.

Accessibility isn't a separate skill bolted onto HTML — it's mostly a byproduct of markup that's genuinely correct, which is why it keeps resurfacing throughout this guide: meaningful alt text, real label associations, a heading outline that doesn't skip levels, semantic landmarks instead of unlabeled <div>s.

Two more tools round this out. tabindex="0" adds an element to the natural tab order when it wouldn't otherwise be focusable — though a real <button> or <a> is almost always a better choice than a styled <div> that needs this fix in the first place. tabindex="-1" makes an element focusable only programmatically, handy for moving keyboard focus after something like a client-side page change. Avoid any tabindex value above 0 — it overrides the natural reading order with a manually maintained one, which quietly breaks the first time the page layout changes.

A "skip to content" link — an <a href="#main"> placed as the very first focusable element, visually hidden until it receives keyboard focus — lets keyboard users bypass repeated navigation on every single page load, rather than tabbing through the same menu every time. And one plain rule worth keeping in mind well beyond HTML: never convey information by color alone, since it's invisible to colorblind visitors and anyone using a screen reader.

<body> <a class="skip-link" href="#main">Skip to content</a> <header>...</header> <nav>...</nav> <main id="main"> <h1>Page content starts here</h1> </main> </body>
  • Correct semantic HTML is most of what "accessible" means in practice.
  • Avoid tabindex values greater than 0 — they create a fragile, manually maintained tab order.
  • A hidden-until-focused skip link saves keyboard users from repeating the same navigation on every page.

Three characters are reserved because HTML uses them for its own syntax: < opens a tag, > closes one, and & starts an entity. To display any of them as literal text rather than have the browser try to parse them, write &lt;, &gt;, and &amp; instead.

Beyond escaping, named entities give you characters that are awkward to type directly: &copy; renders ©, &mdash; renders an em dash —, &hellip; renders an ellipsis …. One entity does real layout work rather than just typography: &nbsp; is a non-breaking space, which glues two words together so they never get split across a line break — useful in things like "10&nbsp;km" or "Mr.&nbsp;Shah."

Since virtually every modern file is saved as UTF-8 (set via the charset meta tag you met earlier), you can generally type accented letters, emoji, and non-Latin scripts directly into your HTML rather than reaching for numeric entities — entities today are mainly for the three reserved characters and a handful of typographically awkward symbols.

<p>Use &lt;strong&gt; for important text, not &lt;b&gt;.</p> <p>&copy; 2026 Studio Verde &mdash; all rights reserved.</p> <p>Race distance: 10&nbsp;km. Doors open at 7&nbsp;am.</p>
  • <, >, and & must be escaped as entities when you mean them literally.
  • &nbsp; stops two words from being separated across a line break.
  • With UTF-8 set, most other special characters can simply be typed directly.

Web Components let you invent your own HTML tags with their own built-in behavior — <user-card>, <rating-stars> — that work anywhere plain HTML works, framework or not. Three technologies cooperate: Custom Elements define the new tag, Shadow DOM (next topic) encapsulates its internal markup and styles, and the <template> element (also next topic) supplies reusable inert markup.

customElements.define('tag-name', ClassName) connects a tag name to a JavaScript class that extends HTMLElement. Custom tag names must contain a hyphen — a deliberate rule ensuring your invented names can never collide with a future standard HTML element, since none of those will ever contain one.

A handful of lifecycle methods fire automatically: connectedCallback() runs when your element is inserted into the page, disconnectedCallback() when it's removed, and attributeChangedCallback() whenever a watched attribute changes — "watched" meaning listed in a static observedAttributes array on the class. You can also extend an existing built-in element (a "customized built-in," written as <button is="fancy-button">), but browser support for that variant is inconsistent, so a brand-new "autonomous" element like the one below is the safer default.

class UserCard extends HTMLElement { static observedAttributes = ['name']; connectedCallback() { this.textContent = 'Loading…'; } attributeChangedCallback(attr, oldVal, newVal) { if (attr === 'name') this.textContent = 'Hi, ' + newVal; } } customElements.define('user-card', UserCard); // Usage in HTML: <user-card name="Amit"></user-card>
  • Custom element tag names must contain a hyphen so they never collide with future standard tags.
  • connectedCallback() runs on insertion; attributeChangedCallback() needs observedAttributes.
  • An "autonomous" brand-new element is generally safer than extending a built-in one, given inconsistent browser support.

<template> holds markup that the browser parses but never renders and never runs — no images inside it load, no scripts inside it execute — until you explicitly clone its .content with JavaScript. That inertness is exactly why it's the right tool for a widget's repeatable markup, instead of assembling the same HTML at runtime out of string concatenation.

Shadow DOM attaches a second, encapsulated DOM tree to an element via element.attachShadow({ mode: 'open' }). Styles and markup placed inside that shadow root are sealed off from the rest of the page: a <style> inside it won't leak out and style your whole document, and most of your page's own CSS won't reach in and affect it either. This is how a custom element ships its own internal look without any risk of colliding with whatever stylesheet the page around it happens to have.

<slot>, used inside a shadow tree, marks exactly where the "light DOM" — the regular children a user places inside your custom element in their own markup — actually gets displayed. It's what lets <user-card>Amit</user-card> keep control over its own internal chrome while still accepting content from whoever uses it.

const tpl = document.createElement('template'); tpl.innerHTML = ` <style> .card { border: 1px solid #ccc; padding: 12px; border-radius: 6px; } </style> <div class="card"><slot></slot></div> `; class FancyCard extends HTMLElement { connectedCallback() { const shadow = this.attachShadow({ mode: 'open' }); shadow.appendChild(tpl.content.cloneNode(true)); } } customElements.define('fancy-card', FancyCard);
  • <template> content is inert — nothing inside loads or runs until it's cloned with JavaScript.
  • Shadow DOM encapsulates a custom element's markup and CSS from the rest of the page in both directions.
  • <slot> is where a custom element's user-supplied content actually renders.

<canvas> and inline <svg> both draw graphics in the browser, but on fundamentally different models. A canvas is a raster surface: you draw onto it imperatively from JavaScript via getContext('2d') and a sequence of draw calls, and once drawn, the browser remembers only pixels — no individual shape objects exist to click, style with CSS, or inspect later. That trade-off makes it well suited to work with a very high number of draw operations: games, real-time charts with thousands of points, image manipulation.

Inline SVG is markup: elements like <circle>, <path>, and <rect> become real, inspectable DOM nodes, each individually stylable with CSS, animatable, and clickable, and resolution-independent at any zoom level since it's vector math rather than pixels. That makes it the better fit for icons, diagrams, logos, and data visualizations with a moderate, human-scale number of shapes.

A simple rule of thumb: reach for SVG when you want elements you can style or script individually and that must stay crisp at any size; reach for canvas when you're drawing so much, or so frequently, that keeping every shape as its own DOM node would be too slow.

<svg viewBox="0 0 24 24" width="24" height="24" fill="none" stroke="currentColor" stroke-width="2"> <circle cx="12" cy="12" r="9"></circle> <path d="M9 12l2 2 4-4"></path> </svg> <!-- A canvas only reserves a drawing surface; JavaScript does the actual drawing --> <canvas id="chart" width="400" height="200"></canvas>
  • Canvas is pixels drawn imperatively via JavaScript — fast at scale, but no per-shape DOM.
  • Inline SVG is real, stylable, resolution-independent DOM elements.
  • Choose SVG for icons/diagrams/charts with modest shape counts; canvas for high-volume or pixel-level work.

Every browser ships two simple key-value stores. localStorage persists until something explicitly clears it, surviving closed tabs and browser restarts; sessionStorage clears automatically when its tab closes. Both only store strings, so objects need JSON.stringify() going in and JSON.parse() coming out, both are synchronous, and both are capped at roughly 5–10MB depending on the browser.

Cookies predate both and are still around mainly because, unlike storage, they're sent automatically with every matching HTTP request to their domain — which is exactly why you should keep them small: anything you store in a cookie adds weight to every single request, not just the page that set it.

For anything larger, more structured, or that needs real querying, IndexedDB is the actual database built into the browser: asynchronous, transactional, and capable of storing far more than localStorage — though its raw API is verbose enough that most projects reach for a small wrapper library rather than using it directly. Offline-capable web apps typically pair storage like this with a service worker, a background script that can intercept network requests and serve cached responses with no connection at all — a substantial topic in its own right, worth a dedicated study once you get here.

// Save const cart = { items: ['mug', 'plate'], total: 850 }; localStorage.setItem('cart', JSON.stringify(cart)); // Read it back later, even after closing the browser const saved = JSON.parse(localStorage.getItem('cart') || 'null'); // sessionStorage has the identical API, but clears when the tab closes sessionStorage.setItem('draftMessage', 'Hey, are we still on for—');
  • localStorage persists indefinitely; sessionStorage clears when the tab closes.
  • Both store strings only — serialize objects with JSON.stringify/JSON.parse.
  • Cookies are sent with every matching request, so keep them small; IndexedDB is the real client-side database.

Any element becomes draggable with a single attribute: draggable="true". From there, a handful of events drive the whole interaction. dragstart fires on the element being picked up — this is where you attach the payload with event.dataTransfer.setData(type, value). dragover fires repeatedly on anything the dragged element passes over, and it must call event.preventDefault() or the browser refuses to allow a drop there at all — this single missing line is the most common reason a drop handler silently never fires. drop fires when the user releases over a valid target, where you read the payload back out with event.dataTransfer.getData(type).

This native API predates most drag-and-drop JavaScript libraries and still underlies real desktop-to-browser interactions, like dropping a file from your file manager onto an upload zone — worth knowing directly even if you reach for a library for something more elaborate, like a fully sortable list.

<div id="card" draggable="true">Drag me</div> <div id="bin" ondragover="event.preventDefault()" ondrop="event.preventDefault(); console.log('dropped')"> Drop here </div>
  • draggable="true" is all it takes to make an element draggable.
  • dragover must call preventDefault() or the drop target will refuse the drop.
  • dataTransfer.setData()/getData() carry the payload between dragstart and drop.
Forgetting event.preventDefault() inside dragover is the single most common reason a drop handler never runs.

ARIA (Accessible Rich Internet Applications) attributes fill gaps for interactive widgets that plain HTML has no native element for — a custom tab panel, a live chat feed, a combobox. The first rule of ARIA is to use as little of it as possible: a real <button> is already fully accessible, while slapping role="button" on a <div> means you now have to manually rebuild keyboard activation, focus styling, and more that the real element already gave you at no cost.

When you genuinely need it: role tells assistive technology what a custom widget behaves like (role="tablist", role="dialog"); aria-expanded="true|false" reports whether a disclosure widget is currently open; aria-live="polite" marks a region so a screen reader announces content that changes inside it — a form's error summary, a live score — without the user needing to navigate there themselves. Landmark roles like role="navigation" largely duplicate what the semantic elements from earlier in this guide already provide, which is one more reason to reach for the real element first.

Focus management deserves special attention for anything that opens on top of the page, like a modal: move keyboard focus into it the moment it opens, keep Tab cycling only within it while it's open, and return focus to whatever triggered it once it closes. Skip any of these three and keyboard users lose their place in the page entirely.

<button aria-expanded="false" aria-controls="panel-1" id="toggle"> Shipping details </button> <div id="panel-1" hidden> Ships within 2 business days via standard courier. </div>
  • Prefer a real HTML element over ARIA-on-a-div whenever one already exists.
  • aria-expanded communicates open/closed state; aria-live announces dynamic changes.
  • Anything that opens like a modal needs focus moved in, trapped, and returned on close.

Where a <script> sits and how it loads has a direct, measurable effect on page speed. A plain <script src="..."> in the <head> blocks HTML parsing completely until it finishes downloading and running. Adding defer downloads it in the background and runs it only after parsing finishes, in source order — a solid default for most scripts. Adding async also downloads in the background, but runs the instant it's ready, potentially out of order relative to other scripts — better suited to fully independent code like analytics snippets.

A family of "resource hints" change when something loads without changing what loads at all. <link rel="preload" as="..."> fetches a resource the browser wouldn't otherwise discover early enough — a font referenced only inside CSS, say. rel="preconnect" opens the network connection (DNS plus TLS handshake) to another origin ahead of the first real request to it; rel="dns-prefetch" does just the DNS lookup, a lighter fallback for older browsers. loading="lazy", met earlier on images and iframes, defers offscreen media until it's about to scroll into view.

<head> <link rel="preconnect" href="https://fonts.gstatic.com" crossorigin> <link rel="preload" as="style" href="/critical.css"> <script src="/app.js" defer></script> <script src="/analytics.js" async></script> </head>
  • defer runs scripts in order, after parsing finishes — a good general default.
  • async runs as soon as a script is ready, potentially out of order.
  • Resource hints (preload/preconnect/dns-prefetch) change timing, not content.

Markup choices carry real security weight. A Content-Security-Policy, set via <meta http-equiv="Content-Security-Policy" content="...">, restricts which sources scripts, styles, and other resources are allowed to load from — meaningfully limiting the damage even if a malicious script does slip onto your page. You already met rel="noopener" for links; the same reasoning applies with more force to iframes, where the sandbox attribute from earlier is your main line of defense.

The classic markup-level vulnerability is writing user-supplied text directly into HTML — via something like element.innerHTML = userComment — without escaping it first. If that comment contains <script>...</script> and you insert it unescaped, that script now runs with full access to your page, your cookies, and anything else on it. Always escape user content before treating it as HTML (turning < into &lt;, exactly like every code sample throughout this guide has been escaped), or better, use element.textContent, which never interprets its input as markup in the first place.

Avoid inline event handler attributes like onclick="..." scattered through your HTML — beyond being harder to maintain, each one is something a strict Content-Security-Policy has to specifically permit, which quietly weakens the exact protection the policy exists to provide.

<meta http-equiv="Content-Security-Policy" content="default-src 'self'; script-src 'self'; object-src 'none'">
  • A CSP meta tag limits what an injected script — if one ever slips through — is able to do.
  • Always escape user-supplied content before inserting it as HTML, or use textContent instead.
  • Avoid inline event handler attributes; they also weaken a strict CSP.
Inserting raw user input via innerHTML without escaping it is the textbook cause of stored cross-site scripting (XSS) vulnerabilities.

Structured data marks up the meaning of your content in a shared, machine-readable vocabulary — mainly schema.org — so search engines can build richer results from it: star ratings, a recipe's cook time, an event's date, shown directly in the search listing itself rather than left for the search engine to guess at.

There are two ways to write it. Microdata attaches itemscope, itemtype, and itemprop attributes directly onto your existing HTML elements, tightly coupling the data to your visible markup. JSON-LD instead lives in a single separate <script type="application/ld+json"> block containing plain structured JSON, fully decoupled from your visible HTML — which is exactly why it has become the generally recommended approach: you can add, update, or correct it without touching your page's markup at all.

Whichever form you use, only describe content that's genuinely present and visible on the page. Marking up information that isn't actually there is treated as manipulative by search engines and risks the page being penalized rather than helped.

<script type="application/ld+json"> { "@context": "https://schema.org", "@type": "Recipe", "name": "Weeknight Dal", "prepTime": "PT10M", "cookTime": "PT25M", "recipeYield": "4 servings" } </script>
  • Structured data helps search engines build richer, more detailed result listings.
  • JSON-LD (a standalone script block) is now generally preferred over inline Microdata attributes.
  • Only mark up content that's genuinely visible on the page itself.

A handful of relatively recent elements replace what used to require hand-rolled JavaScript. <details> paired with a nested <summary> creates a native disclosure widget — click the summary to expand or collapse everything else inside, with full keyboard support and zero JavaScript; add the boolean open attribute to start it expanded.

<dialog> is a native modal (or non-modal) window. Calling its .showModal() method from JavaScript opens it with an automatic backdrop, focus trapped inside it, and the Escape key already wired up to close it — a genuinely large amount of the accessibility work you'd otherwise have to hand-build for a custom modal, delivered by the browser itself. Call .close() to dismiss it programmatically.

The popover attribute, paired with a triggering button's popovertarget attribute, creates a lightweight floating layer — a tooltip, a menu, a non-modal hint — that the browser automatically renders above everything else and dismisses on an outside click or Escape, again without a line of JavaScript for the basic case. You already met <template>, for inert, cloneable markup, back in the Web Components topics.

<details> <summary>What's your return policy?</summary> <p>Unused items can be returned within 30 days with a receipt.</p> </details> <button popovertarget="tip">Why do we ask?</button> <div id="tip" popover>We only use this to size your recommendation.</div>
  • <details>/<summary> is a native, keyboard-accessible disclosure widget — no script needed.
  • <dialog>'s .showModal() handles backdrop, focus trapping, and Escape-to-close natively.
  • The popover attribute creates a dismissible floating layer without any JavaScript.

It's worth closing the loop on where all of this actually goes. When a browser receives your HTML, it parses it into the DOM — a tree of node objects, one per element, attribute, and piece of text — which is the literal structure that CSS selectors match against and that document.querySelector and friends return. In parallel, the browser builds a similar tree from your CSS, the CSSOM. The two combine into a render tree describing exactly what should appear, which the browser then lays out — computing sizes and positions — and finally paints to the screen.

This is precisely why script placement, covered in the performance topic, has a real effect rather than being a matter of style: a <script> without defer or async, sitting in the middle of your HTML, pauses this entire parse-build-layout-paint sequence to fetch and run.

One practical payoff: "inspecting an element" in your browser's developer tools is really just browsing this exact DOM tree live. It's frequently faster to read the current DOM there than to re-read your own HTML source, especially once JavaScript has modified the page after the initial load.

  • The browser parses HTML into the DOM and CSS into the CSSOM.
  • Those two trees combine into a render tree, which is laid out and then painted.
  • A render-blocking script pauses this whole sequence — the real reason defer/async matter.
  • Devtools' element inspector shows this same live DOM tree, not your original source file.

Sixteen questions that come up often in real interviews, drawn from across every tier of this guide. Click a question to reveal a concise model answer — try answering in your own words first.

What is semantic HTML, and why does it matter?

Markup chosen for what it means rather than how it looks — <nav> instead of a generic <div class="nav">. It matters because browsers, screen readers, and search engines all use that meaning: for navigation, document outlines, and search result quality.

What's the difference between an element being "block" and "inline"?

A block-level element (like <p> or <div>) starts on its own line and takes the full available width by default. An inline element (like <span> or <a>) flows within a line of text and only takes as much width as its content needs.

What's the difference between id and class?

id must be unique within the page and is used for anchors, label associations, and single-element hooks. class can be reused across many elements and can hold multiple space-separated values on one element.

Why is the alt attribute on images important?

It's read aloud by screen readers, shown if the image fails to load, and used by search engines. Purely decorative images should get an empty alt="" rather than no alt at all.

What happens if the browser encounters a tag it doesn't recognize?

It treats it as an unknown, un-styled inline element and keeps rendering the rest of the page normally — HTML parsing is deliberately fault-tolerant. This is also exactly how custom elements are able to work before their JavaScript definition has loaded.

What's the difference between <script>, defer, and async?

A plain script blocks HTML parsing while it downloads and runs. defer downloads in the background and runs after parsing finishes, in order. async downloads in the background too, but runs the instant it's ready, potentially out of order.

What's the difference between localStorage, sessionStorage, and cookies?

localStorage persists until cleared; sessionStorage clears when the tab closes; both store strings client-side only. Cookies are smaller, and unlike storage, are sent automatically with every matching HTTP request.

What's the difference between the hidden attribute and CSS display: none?

They produce the same visual result, but hidden is HTML — it expresses "this isn't relevant right now" directly in your markup with no CSS required, while display: none is a styling decision. Both remove the element from the accessibility tree.

Why prefer <strong> over <b>, or <em> over <i>?

<strong>/<em> carry semantic weight that assistive technology can act on; <b>/<i> are purely visual with no claim about importance or emphasis.

What does the viewport meta tag actually do?

<meta name="viewport" content="width=device-width, initial-scale=1.0"> tells mobile browsers to render at the device's real width instead of a fake 980px-wide desktop layout that then gets zoomed out — without it, responsive CSS breakpoints won't behave correctly on phones.

When would you use GET versus POST on a form?

GET appends form data to the URL and suits read-like, idempotent requests such as a search box. POST sends data in the request body and suits anything that changes server state, like creating an account or placing an order.

What does <!DOCTYPE html> actually do?

It switches the browser into standards-compliant rendering mode. Without it, older "quirks mode" rendering kicks in, with inconsistent, legacy behavior around sizing and layout.

What is Shadow DOM, in one sentence?

A separate, encapsulated DOM tree attached to an element, so its internal markup and CSS don't leak out to the page and the page's CSS mostly can't leak in — the mechanism that lets custom elements ship self-contained styling.

Why avoid inline event handlers like onclick="..."?

They mix behavior into structure, are harder to maintain and reuse, and each one is something a strict Content-Security-Policy has to specifically allow — weakening the exact protection that policy exists to provide.

What's the difference between srcset/sizes and <picture>?

srcset/sizes on a plain <img> handles resolution switching — the same crop at different sizes. <picture> handles art direction — genuinely different crops at different breakpoints.

What is a void element? Name a few.

An element that can never have children and therefore has no closing tag: <br>, <img>, <input>, <hr>, <meta>, and <link> are the common ones.

Reading a guide gets you to recognition; writing markup from scratch gets you to fluency. A few ways to close that gap:

  • Build a small personal portfolio page using only semantic HTML — no CSS at all yet — and check that it reads sensibly in outline form.
  • Pick a real website you use daily, view its source, and try to explain why each major section uses the tag it does.
  • Take a video you've made or found and add real <track> captions to it.
  • Build one small custom element from the Web Components topics — a <rating-stars> or <countdown-timer> is a good first project.
  • Run any page you build through the W3C Markup Validator and an accessibility checker like axe DevTools or Lighthouse, and fix every warning rather than only the errors.

Because HTML is a living standard, treat MDN (developer.mozilla.org) as your ongoing reference for exact, current syntax whenever you need it — this guide is a foundation to build fluency on, not the last word on any single tag.
